# ARC-002 태그는 서버가 자동으로만 붙이고, 사용자는 보고 `#태그`로 찾거나 지울 수 있다
- 상태: 검토 중 (개발자 확인 대기)
- 적용 범위: 모든 플랫폼의 자료 목록·자세히 보기, `찾기`. 태그는 저장 뒤 처리 단계에서 서버가 만든다

> **요약** 서버는 요약을 만들 때 자료마다 태그를 최대 5개 만든다. 사용자는 목록과 자세히 보기에서 태그를 보고 `찾기 #태그`로 걸러 찾을 수 있다. 틀린 태그는 지울 수 있지만, 태그를 직접 붙이거나 고치지는 않는다.

## 용어

| 용어 | 뜻 |
| :--- | :--- |
| 태그 | 서버가 자료 내용에서 뽑아 붙인 짧은 낱말. 화면에는 `#결제`처럼 앞에 `#`을 붙여 보인다 |
| 태그 찾기 | `찾기` 검색어 중 `#`으로 시작하는 낱말로 자료를 거르는 것 |

## 규칙

1. 서버는 요약을 만드는 같은 처리에서 태그를 만든다(ADR-BCK-008). 외부 LLM으로 보내는 범위는 COM-002를 따른다.
2. 사용자가 태그를 붙이거나 고치는 명령은 두지 않는다. `고치기 <번호> -#태그`로 태그를 지우는 것만 둔다. 지운 태그는 그 자료에 다시 붙이지 않는다.
3. `고치기`로 제목·요약을 고쳐도, 서버는 태그를 다시 만들지 않는다.
4. 자료 목록의 각 줄 끝에는 태그를 앞에서부터 3개까지 보여 준다. 자세히 보기에는 모두 보여 준다.
5. `찾기 #결제`는 태그가 정확히 `결제`인 자료만 찾는다. 영문은 대소문자를 가리지 않는다.
6. `#태그`를 여러 개 쓰거나 일반 검색어와 함께 쓰면, 모든 조건에 맞는 자료만 찾는다(AND).
7. `#` 없는 일반 검색어는 제목·본문·요약·이미지 속 글자와 함께 태그에서도 찾는다.
8. 태그가 아직 없는 자료(처리 중, 처리 실패, 아직 요약하지 않은 북마크 가져오기 자료)는 태그 찾기에 나오지 않는다. 태그를 만들지 못해도 사용자에게 따로 알리지 않는다.
9. 넘길 글에는 태그를 넣지 않는다.
10. 서버는 특정 사람의 건강·질병, 정치 성향, 종교, 노동조합 가입, 성생활, 범죄 경력 같은 민감정보를 추론하는 태그를 만들지 않는다. 주제 자체를 가리키는 태그(`#의학`, `#선거`)는 만들 수 있다.
11. 태그는 AI가 추정한 검색 보조 값이다. 화면에 태그를 보여 줄 때는 ARC-004의 AI 생성 표시를 따른다.
12. `고치기`로 제목·요약을 고치거나 태그를 지워도, 고치기 전 제목·요약과 지운 태그 낱말은 `#` 없는 일반 검색어로 계속 찾힌다. `찾기 #태그`에는 지운 태그로 나오지 않는다.

## 값

| 항목 | 값 | 경계 |
| :--- | :--- | :--- |
| 자료당 태그 수 | 0~5개 | 5개를 넘게 만들면 앞 5개만 저장한다 |
| 목록에 보이는 태그 수 | 3개 | 나머지는 자세히 보기에서 |
| 태그 하나 길이 | 1~20자 | 띄어쓰기 없음. 20자를 넘는 태그는 버린다 |
| 태그 글자 | 한국어 우선. 영문은 소문자 | 띄어쓰기와 `#`은 들어가지 않는다 |

## 근거

- PO 결정(2026-11-26): 자동 태그를 보이기만 한다. 자료당 최대 5개, 목록에는 3개. 사용자가 직접 붙이거나 고치지 않는다. 새 명령은 두지 않는다
- 기획서 F2(자동 태그), STATE 11절(자동 태그는 내부 재료였음, E-11: 태그로 찾기는 성공률이 낮고 느림. 그래서 직접 태그 관리는 넣지 않음)
- PO 결정(2026-11-28): 고치기 뒤에도 옛 제목·요약과 지운 태그 낱말이 일반 찾기로 찾히는 지금 동작을 그대로 둔다(규칙 12, [QA 검수 보고](../../planning/qa-2026-11-28-demo-readiness.md) Q-7)
- 구현: `찾기`의 검색어·`#태그` 나누기와 `태그 없음` 줄은 `core/Features/Terminal/Sources/Commands/SeekCommand.swift`, 서버 검색은 `PgroongaItemSearch.kt`(#61). 태그를 만드는 처리(규칙 1)는 `server/src/main/kotlin/com/unwrap/grep/features/processing/adapters/gemini/GeminiSummarizer.kt`, 값 표대로 정리하는 곳은 `server/src/main/kotlin/com/unwrap/grep/features/processing/domain/Tags.kt`(#59). 규칙 12는 `server/src/main/kotlin/com/unwrap/grep/features/archive/adapters/postgres/JdbcItemRevisionRepository.kt`(검색 글에 고친 제목·요약을 덧붙이기만 함)

## 검증 방법

| 종류 | 확인할 것 |
| :--- | :--- |
| 자동 테스트 | `#태그` 여러 개와 일반 검색어를 섞었을 때 AND로 거르는지, 영문 대소문자를 가리지 않는지 |
| 자동 테스트 | 태그가 5개를 넘거나 20자를 넘을 때 잘리고 버려지는지 |
| 자동 테스트 | `고치기` 뒤 옛 제목 낱말로 일반 `찾기`를 하면 나오고, 지운 태그로 `찾기 #태그`를 하면 나오지 않는지(규칙 12) |
| 수동 확인 | 사람에 관한 자료(인물 기사, 진단서 예시 등)로 민감정보 추론 태그가 나오지 않는지. 태그를 만드는 프롬프트에 금지 범주가 들어 있는지 |
| 수동 확인 | 목록 한 줄에 태그 3개가 들어가도 터미널 폭에서 줄이 깨지지 않는지 |

## 비고

- 태그 목록을 보는 명령, 사용자의 직접 태그는 이번에 두지 않는다. 필요하면 이 정책을 수정한다.
- 목록 태그는 모든 목록(`최근`, `찾기`, 묶음 안 자료)에 앞 3개를 보인다. 명령어 설명서의 "검색어와 일치한 것만" 안을 대체한다. 웹 자세히 보기는 발표 뒤에 만든다. 그때까지 웹에서 태그 4·5번째는 볼 곳이 없다(2026-11-26 PO 결정, AI 제안 수용).
- 잘못 붙은 태그는 `고치기 <번호> -#태그`로 지운다(2026-11-26 PO 결정). 개발자 확인할 것: 명령 문법, 지운 태그를 기억해 다시 붙이지 않는 방법.
- 태그 생성 방식이 바뀌어도 기존 자료의 태그는 다시 만들지 않는다. 다시 만들려면 이 정책에 적고 한다.
- 규칙 12의 이유(개발 메모): 본문 일부를 따로 저장하지 않아 검색 글을 다시 모을 수 없다. 찾기 정확도 불만이 나오면 본문 칸을 따로 두고 다시 모으는 방식으로 바꾸고 이 규칙을 고친다.
