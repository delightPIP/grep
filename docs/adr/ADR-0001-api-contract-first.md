### ADR-0001 프론트엔드와 백엔드는 OpenAPI 계약으로만 연결하고, 서비스 규칙은 서버가 최종 판정한다
- 상태: 채택
- 날짜: 2026-11-25
- 영역: 공통

> **요약** 클라이언트(앱·웹·MCP)와 서버는 레포에 둔 OpenAPI 스펙으로만 연결한다. 중복 판정, 검증, 권한, 한도, 삭제는 서버가 최종 판정하고, 모든 클라이언트에서 같아야 하는 산출물(넘길 글)은 서버가 만든다.

#### 배경

팀은 Android, iOS, Web, Windows 네 플랫폼을 원하고([기획서](../planning/PRD.md) 7절), AI 도구도 MCP로 서버에 접속한다(F7). 클라이언트는 플랫폼별 뷰와 공유 코어로 만들 계획이지만 아직 정하지 않았다. 클라이언트 기술과 서버 기술을 서로 묶지 않고 따로 정하고 바꿀 수 있어야 한다.

#### 결정

1. OpenAPI 스펙 파일을 레포에 두고 단일 출처로 삼는다. 스펙을 먼저 고치고 구현이 따른다.
2. 중복 판정(정규화한 URL, 파일 해시), 입력 검증, 권한, 용량 한도, 삭제 처리는 서버가 최종 판정한다. 클라이언트의 판정은 화면을 빨리 보여 주기 위한 것이다.
3. 서버는 클라이언트 종류에 따라 분기하지 않는다.
4. 모든 클라이언트에서 같아야 하는 산출물(넘길 글)은 서버 엔드포인트로 제공한다. 앱의 `copy`와 MCP가 같은 결과를 낸다.
5. 하위 호환을 지킨다. 필드는 추가만 하고, 깨지는 변경은 새 버전 경로로 낸다.
6. 오류 응답은 RFC 9457(Problem Details) 형식으로 통일한다.
7. 서버 언어 밖에서 HTTP로만 검사하는 API 테스트와, 같은 결과가 나와야 하는 함수의 테스트 벡터(입력과 기대 출력 JSON)를 둔다.

#### 고려한 대안

| 대안 | 기각 이유 |
| :--- | :--- |
| 코드에서 스펙을 생성 (코드 우선) | 스펙이 서버 언어와 프레임워크에 묶여 서버 언어를 바꾸기 어렵다 |
| 클라이언트와 서버가 같은 언어로 규칙 코드를 공유 | 프론트와 백엔드의 기술 선택이 서로 묶인다 |
| 넘길 글을 클라이언트가 생성 | 플랫폼마다, 그리고 MCP와 형식이 어긋날 수 있다 |
| GraphQL | 한 사용자의 작은 데이터를 조회하는 데 이득이 적고, MCP·캐시·도구 구성이 복잡해진다 |

#### 결과

- 얻는 것: 클라이언트와 서버의 기술을 따로 정하고 바꿀 수 있다. 서버 언어를 바꿔도 같은 API 테스트로 완료를 판정한다. MCP를 포함한 모든 클라이언트가 같은 규칙과 같은 넘길 글을 쓴다.
- 비용: 스펙을 따로 관리하고 코드 생성 도구를 설정해야 한다. 넘길 글이 서버에 의존하므로 오프라인에서는 `copy`가 되지 않는다(기획서 10절의 오프라인 동작과 같다). 오프라인 `copy`가 필요해지면 형식을 테스트 벡터로 계약에 넣어야 한다.
