### ADR-BCK-004 서버는 기능별 모듈러 모놀리스로 만들고, 모듈 안은 포트와 어댑터로 나눈다
- 상태: 채택
- 날짜: 2026-11-25
- 영역: 백엔드

> **요약** 한 코드베이스와 한 DB를 쓰되, 기능별 모듈로 먼저 나누고 각 모듈 안을 도메인, 포트, 어댑터로 나눈다. 같은 모듈 묶음으로 API 서버, 워커, MCP 서버 세 프로세스를 띄운다.

#### 배경

개발자는 iOS에서 MicroFeature, Clean Architecture, RIBs 구조를 쓴다. 같은 방식으로 생각하고 테스트할 수 있는 서버 구조가 필요하다. 개발자는 1명이고, API, 백그라운드 처리, MCP가 같은 데이터와 규칙을 쓴다.

#### 결정

1. 모듈러 모놀리스로 만든다. 기능 모듈은 `ingest`, `archive`, `processing`, `bundle`, `sync`, `mcp`, `metrics`이고, 여기에 `shared/kernel`과 조립 지점 `app`을 둔다.
2. 각 기능 모듈은 `interface`(다른 모듈에 공개하는 포트, DTO, 이벤트), `domain`(엔티티, 유스케이스), `adapters`(HTTP, Postgres, 스토리지, LLM), `testing`(가짜 구현과 픽스처)으로 나눈다.
3. 다른 모듈의 `interface`에만 의존한다. 다른 모듈의 테이블을 직접 읽지 않는다. 의존 방향은 `app → features → shared/kernel`이고 순환은 없다.
4. 모듈 사이의 비동기 연결은 Postgres에 기록한 이벤트와 작업으로 한다(ADR-BCK-002).
5. API 서버, 워커, MCP 서버는 같은 모듈을 쓰는 서로 다른 진입점이다. `mcp`는 들어오는 어댑터만 갖는다.
6. 경계는 Gradle 모듈로 강제한다. MVP에서는 `interface`를 다른 모듈이 실제로 쓰는 곳에만 둔다.

#### 고려한 대안

| 대안 | 기각 이유 |
| :--- | :--- |
| 마이크로서비스 | 이 규모에서는 배포, 네트워크, 분산 트랜잭션 비용만 늘어난다 |
| 계층 우선 구조 (`domain`, `infrastructure`, `api`가 모든 기능을 가로지름) | 기능이 늘수록 한 기능의 변경이 여러 모듈에 퍼진다 |
| 모듈 하나에 패키지로만 구분 | 경계를 강제할 수 없다 |

#### 결과

- 얻는 것: iOS의 MicroFeature(Interface/Sources/Testing)와 같은 방식으로 생각하고 테스트한다. 모듈 단위로 떼어 서비스로 분리하거나 다른 언어로 옮길 수 있다. 워커와 API를 따로 늘릴 수 있다.
- 비용: Gradle 설정과 보일러플레이트가 늘어난다. 초기 모듈 경계를 잘못 그으면 다시 나누는 비용이 든다.

#### 관련

ADR-BCK-002, ADR-BCK-003, ADR-0001
