### ADR-BCK-002 자료와 작업 큐는 Postgres 하나에, 파일은 오브젝트 스토리지에 둔다
- 상태: 채택
- 날짜: 2026-11-25
- 영역: 백엔드

> **요약** 자료, 묶음, 작업 큐, 이벤트를 Postgres 하나에 두고 행 단위 접근 제어(RLS)로 사용자를 격리한다. 파일은 오브젝트 스토리지에 두며, Redis, 메시지 큐, 검색 엔진은 쓰지 않는다.

#### 배경

데이터 특성을 10축으로 분석했다([백엔드 설계](../../planning/backend-design.md) 3절).

- 사용자별로 격리된 개인 데이터이고, 한 사용자당 수천 건 규모이며 핫키가 없다.
- 쓰기가 몰리는 곳은 여러 파일 던지기와 북마크 가져오기 두 곳뿐이다.
- 어려운 부분은 외부 의존이 많은 "저장 뒤 처리"(본문 가져오기, 추출, 요약)다.
- 자료, 묶음, 처리 상태는 관계형이고, 형식별 메타데이터는 형태가 제각각이다.

#### 결정

1. 자료, 묶음, 작업 큐, 이벤트를 Postgres 하나에 둔다. 사용자 격리는 RLS로 DB에서도 강제한다.
2. 파일은 S3 호환 오브젝트 스토리지에 두고, 클라이언트가 서명된 URL로 직접 올린다.
3. 작업 큐는 Postgres 테이블에 `FOR UPDATE SKIP LOCKED`와 리스(lease)로 만든다. 자료 행과 작업 행을 같은 트랜잭션에 쓴다.
4. 검색은 MVP에서 사용자 범위로 좁힌 부분 문자열 검색으로 시작한다. 사용자당 건수가 늘면 PGroonga나 pg_trgm으로 바꾸고, 의미 검색은 pgvector로 붙인다.
5. 스키마 마이그레이션은 순수 SQL 파일로 관리한다.
6. Redis, Kafka 같은 메시지 큐, Elasticsearch 같은 검색 엔진, 읽기 복제본은 쓰지 않는다.

#### 고려한 대안

| 대안 | 기각 이유 |
| :--- | :--- |
| MySQL | 한국어 ngram 검색이 내장된 장점은 있다. 그러나 RLS가 없어 격리를 앱 코드로만 지켜야 하고, 벡터 검색 생태계가 약하다 |
| SQLite (Turso 등) | API와 워커가 동시에 쓰는 구조에 맞지 않는다 |
| MongoDB, Firestore | 묶음 같은 관계형 데이터, 작업 큐, 한국어 검색에 불리하다 |
| 외부 메시지 큐 (Redis, Kafka 등) | DB 쓰기와 큐 발행 중 하나만 성공하는 불일치(dual write)를 막으려면 Outbox가 필요하고, 운영 대상이 하나 늘어난다 |
| 별도 검색 엔진 | 한 사용자 수천 건 규모에는 운영 부담만 크다 |

#### 결과

- 얻는 것: 운영 대상이 DB와 스토리지 둘뿐이다. 자료와 작업이 같은 트랜잭션에 들어가 Outbox가 필요 없다. 검색과 벡터를 확장으로 붙일 수 있다. 관리형 서비스와 무료 플랜이 많다.
- 비용: 한국어 검색 품질은 확장(PGroonga 등)에 기대야 한다. Postgres 큐는 처리량에 한계가 있다(이 규모에서는 문제가 되지 않는다). 어느 관리형 서비스를 쓸지(Supabase 등)는 아직 정하지 않았다.
