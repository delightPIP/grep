### ADR-BCK-006 DB, 인증, 파일 저장소는 Supabase를 쓰고, Supabase 전용 기능에는 묶이지 않는다
- 상태: 채택
- 날짜: 2026-11-25
- 영역: 백엔드

> **요약** Postgres, 인증, 파일 저장소는 Supabase를 쓴다. 클라이언트는 로그인에만 Supabase를 쓰고 데이터는 Kotlin 서버로만 주고받는다. RLS, 사용자 테이블, 파일 접근은 다른 서비스로 옮길 수 있는 형태로 만든다.

#### 배경

ADR-BCK-002는 Postgres와 오브젝트 스토리지를 정했지만 어떤 관리형 서비스를 쓸지는 남겨 두었다. 발표(2026-12-01)까지 6일 안에 서버와 웹을 만들어야 하므로 인증과 파일 저장소를 직접 만들 시간이 없다. 나중에 다른 서비스(Neon과 Clerk과 R2 조합, AWS 등)로 옮길 가능성은 열어 둔다.

#### 결정

1. Postgres, 인증, 파일 저장소에 Supabase를 쓴다. Kotlin 서버는 Supabase 밖에서 호스팅한다.
2. Realtime, Edge Functions, 클라이언트의 직접 DB 조회(`supabase-js` 데이터 API)는 쓰지 않는다. 클라이언트는 로그인에만 Supabase를 쓰고, 데이터는 Kotlin 서버 API로만 주고받는다(ADR-0001).
3. 사용자 정보는 자체 `users` 테이블에 두고 외부 인증 ID만 저장한다. Supabase의 `auth.users`를 외래 키로 참조하지 않는다.
4. RLS 정책은 Supabase의 `auth.uid()`를 직접 부르지 않고 우리가 정의한 함수를 거친다.
5. 서버는 표준 JWT 검증(JWKS)으로 사용자를 확인한다. Supabase 전용 서버 SDK에 의존하지 않는다.
6. 파일은 S3 호환 API로 접근한다.
7. 클라이언트의 로그인 코드는 한 모듈에 모은다.

#### 고려한 대안

| 대안 | 기각 이유 |
| :--- | :--- |
| Neon(DB) + Clerk(인증) + Cloudflare R2(파일) | 각 분야에서 강하지만 연결할 서비스가 셋이라 설정 시간이 들고, RLS에 인증 정보를 직접 넘겨야 한다. 나중에 옮겨 갈 1순위 후보로 둔다 |
| Nhost | Supabase와 비슷한 일체형이지만 GraphQL 중심이라 OpenAPI 계약(ADR-0001)과 결이 다르다 |
| AWS (RDS, Cognito, S3) | 네트워크·권한·비밀 관리 설정에 1~2일이 들고, 상시 요금이 나간다 |
| Firebase, PocketBase, Appwrite | Postgres가 아니라 ADR-BCK-002와 맞지 않는다 |
| 인증과 파일 저장소를 직접 구성 | 6일 일정에 들어가지 않는다 |

#### 결과

- 얻는 것: 인증과 파일 저장소를 만들지 않아도 된다. 무료 플랜으로 시작할 수 있다. 결정 2~7을 지키면 옮기는 비용이 대략 DB 반나절, 파일 반나절과 복사 시간, 인증 1~3일(사용자 재로그인)이다. AWS로 옮길 때는 기반 설정을 포함해 3~5일로 추정한다.
- 비용: 무료 플랜은 7일 동안 활동이 없으면 일시 정지되고, DB와 파일 용량 한도가 작다(검색 결과 기준 DB 500MB, 파일 1GB). 한국어 검색에 PGroonga를 쓰면 AWS RDS로 옮길 때 다른 방식으로 바꿔야 할 수 있다. Supabase 저장소의 S3 호환 지원은 확인이 필요하다.

#### 관련

ADR-0001, ADR-BCK-002, ADR-BCK-003
