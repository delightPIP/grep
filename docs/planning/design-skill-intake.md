## 세 자료가 모두 같은 말을 한 것 (스킬의 고정 핵심)

세 자료가 따로 썼는데도 일치한 규칙이다. 스킬에서 가장 먼저, 예외 없이 지킨다.

1. 문제 정의에 해결책("AI로")을 넣지 않고, AI를 쓸지는 비AI 대안(규칙·검색·템플릿)과 비교해 정한다
2. 문장마다 사실·해석·가정(D3는 미확인 추가)을 가르고, 출처 없는 숫자를 만들지 않는다. 없으면 TBD와 확인 대상
3. 레퍼런스는 외형이 아니라 "푸는 문제·한계·우리와 차이·옮길 원칙"으로 뜯어 본다
4. 정상 화면 하나가 아니라 상태 전체(결과 없음·오류·거절·취소·되돌리기·사람 확인)를 정의하고, 결과 없음·오류·거절은 서로 다른 문구와 행동으로 나눈다
5. AI 결과가 원본·입력을 덮어쓰지 않는다. 실패해도 입력은 남는다
6. 결정은 생각의 흐름이 아니라 대안·근거·가정·감수한 것·재검토 조건으로 남긴다
7. 수용 기준은 Given-When-Then으로, 관찰 가능한 결과로
8. 스킬은 SKILL.md(규칙)와 템플릿·점검표·예시를 나눈다

## D1. AI 기능 UI/UX 설계 표준 프로세스

### 한 줄 요지

화면을 그리기 전에 AI 적합성, 매번 달라지는 출력, 지연, 예외 상태, 사용자 통제권을 먼저 정하고, 6단계(기획 → 리서치·레퍼런스 해체 → AI 경험 설계 → UX/UI 구체화 → 검증 → 핸드오프)를 단계별 진입 기준(Gate)으로 묶는다.

|---|---|---|

| 근거 3단 태그 | 2.2-3 | `[Fact | 출처·확인 상태]` `[Insight]` `[Assumption | 검증 방법]`. 출처 없는 숫자 금지 |

### 버릴 것

- 원문 예시 숫자(CS 210건 중 68건, 수락률 90% 등): 예시일 뿐 근거가 아니다. 스킬 예시로도 옮기지 않는다(옮기면 사실처럼 읽힘)
- 3~4주 풀 트랙 일정, 경영진 리뷰, 출시 2주 차 로그 회고: 프로젝트 범위 밖
- 원문 SKILL 초안을 통째로 쓰는 것: 한 파일에 다 들어 있어 길다. SKILL.md에는 순서와 판단 규칙만, 템플릿·상태표·점검표는 참고 파일로 나눈다

### 그렙에 대 보면 바로 보이는 것 (스킬 시험용 사례)

- 8대 상태를 그렙 "요약" 기능에 대 보면: 오류·결과 없음은 ARC-005·ARC-004(요약 없음 이유 표기)가 있다. 초기 유도(자료 0건 첫 화면)는 디자이너 검토 B2에서 다뤘다. **재시도(처리 다시 시키기)는 ARC-005 규칙 9로 "지금은 없음"** — 스킬이 이것을 빈칸으로 잡아내고 "정책상 의도적으로 없음"으로 구분해야 한다
- 사람 확인(HITL): 그렙은 외부로 보내는 동작이 `넘기기`(클립보드 복사)뿐이고 붙여 넣기는 사용자가 한다. 원문의 "외부 발송 전 승인"과 같은 효과가 구조로 이미 있다
- 이 두 사례를 스킬 완성 뒤 시험 입력으로 쓴다

## D2. 기획부터 인계·운영까지 7단계 (가상 사례: 상담원 답변 초안)

### 한 줄 요지

첫 산출물은 AI 화면이 아니라 "사용자가 지금 하는 일과 AI가 이겨야 할 비교 대상"이다. AI를 안 쓰는 결론도 정상 결과로 본다.

### D1에 없던 것 — 가져갈 것

| 요소 | 원문 위치 | 스킬에서 쓰는 방식 |
|---|---|---|
| 문제 정의 한 문장 틀 | P1 완료 기준 | "[사용자]가 [상황]에서 [과업]을 끝낼 때 생기는 [문제]를, [현재 대안]보다 개선하되 [피해야 할 피해]는 늘리지 않는다." P1 통과 조건으로 쓴다 |
| 답을 4가지로 나누기 | P1 판단 기준 | 확인된 요구 / 희망 / 검증할 가정 / 충돌. 충돌은 어느 쪽으로도 확정하지 않고 "영향 받는 범위만 보류"로 적는다 |
| 미확인 ≠ 없음 | P2 경쟁 조사 | 보지 못한 기능을 "없음"으로 쓰지 않는다 |
| 레퍼런스는 전후 3장 | P2 이미지 | 직전 화면 → 사용자 행동 → 직후 결과. 공유 가능 범위도 적는다 |
| 성과 지표와 악화 감시 지표 짝 | P3 지표 표 | 지표마다 분모·측정 구간·제외 조건. 생성 속도·클릭률만으로 성공 판단 금지 |
| 상태 5칸 | P4 완료 기준 | 진입 조건 / 표시 / 허용·금지 행동 / 다음 상태 / 원본 영향 |
| 새 상태 | P4 표 | S-UNVERIFIED(근거 부족·상충), S-CANCEL(취소 뒤 늦게 온 응답은 반영 안 함), S-APPLIED(반영했지만 아직 안 보냄), S-HANDOFF(사람에게 넘김) |
| 화면이 약속 못 할 것 | P4 | 측정 근거 없는 진행률·남은 시간 표시 금지. 개발이 보장 못 하는 동작(서버 취소 등)을 화면에서 약속하지 않음 |
| 검증 두 갈래 | P6 | 사용성 테스트와 AI 품질 평가를 따로 판정. 판정은 지지 / 반박 / 판단 불가 |
| 승인 범위 단계 | P7, 템플릿 머리말 | 설계 검토 가능 / 개발 착수 가능 / 출시 가능을 따로 둔다 |
| 실행 모드 4개 | 5절 | 탐색 / 전체 설계 / 기존 설계 리뷰 / 변경분 갱신. 그렙은 리뷰·변경분 갱신을 가장 자주 쓸 것 |
| 출력 첫 표 | 5절 출력 계약 | 단계 / 현재 확인 상태 / 막힌 결정 / 다음 행동 |
| 스킬 회귀 시험 3개 | 5절 끝 | ① 고정 문구 찾기 → 검색 대안을 빠뜨리지 않는가 ② 발송 권한 미확인 → 발송 분기만 보류하는가 ③ 이미지 한 장 → 사용자 선호·효과를 지어내지 않는가. checks/에 그대로 넣는다 |
| 결정 기록 깊이 | 6절 끝 D-01 예 | 제안/승인 구분, 근거, 가정, 버린 대안, 감수하는 비용, 재검토 조건. 그렙 ADR 형식과 거의 같다 |

### 그렙에 맞게 바꿀 것

| 원문 | 그렙 사정 | 바꾸는 방법 |
|---|---|---|
| P6 사용자 과업 테스트(교차 순서, 실제 역할 참여자) | 인터뷰·실사용자 없음 | "판단 불가"로 남기는 것이 정직하다. 발표 리허설의 5초 테스트는 방향 확인으로만 적는다 |
| P7 제한 배포·모니터링·중단 계획 | 발표까지가 범위 | "AI 처리를 꺼도 기존 경로가 되는가"만 남긴다. 그렙은 ARC-005 규칙 8(`blocked`·`failed` 자료도 똑같이 씀)로 이미 답이 있다 |
| 운영·정책·보안 리뷰어 | 2인 팀 | 검토 역할은 PO·개발 |
| 템플릿 8절 인계·운영 | 범위 밖 | 그렙 버전에서는 빼거나 한 줄로 |

### 그렙에 대 보면 (시험용 사례 추가)

- **P3 비AI 결론의 실제 예**: `찾기`는 AI가 아니라 PGroonga 부분 문자열 검색이다(ADR-BCK-002, 의미 검색은 나중에 pgvector로 "붙일 수 있음"). 스킬에 "왜 찾기는 AI가 아닌가"를 넣으면 P3 판단 사례가 된다. 다만 그 판단 기록이 ADR에 대안 비교로 남아 있는지는 확인 안 함
- **S-APPLIED와 발송 분리**: 그렙 `넘기기`는 클립보드 복사까지만 하고 AI 도구에 붙여 넣는 건 사용자다. D2가 강조하는 "반영 ≠ 발송"이 구조로 이미 지켜진다. 상태 문구가 "보냈다"로 읽히지 않는지는 점검 대상(넘기기 결과 화면, 디자이너 검토 A2)
- **S-UNVERIFIED**: 요약이 원문과 다를 수 있다는 표시는 ARC-004(AI 생성 표시)가 맡는다. 근거 대조(원문 링크로 가기)가 화면에 있는지 확인할 것

### 버릴 것·주의

- 외부 출처 6개(Google Rules of ML, Microsoft Human-AI 지침, NIST AI 600-1, WCAG 2.2, GOV.UK, Outlook 도움말): 실제 있는 자료로 보이지만 **이번에 링크를 열어 확인하지 않았다.** 스킬에 근거로 넣으려면 `it-service-planner:evidence-review`로 원문 확인 뒤에 넣는다. WCAG 기준 번호(1.4.1, 2.1.1, 2.4.3, 2.4.7, 3.3.1, 4.1.3)는 체크리스트 후보
- 상담원 가상 사례: 스킬 예시로는 좋지만, 그렙 스킬이면 그렙 사례로 바꾼다

## D3. 6단계 + 템플릿 4종 + 산출물 27개

### 한 줄 요지

D1의 6단계 뼈대에 D2의 정직함(미확인 라벨, 해당 없음 표시)을 더하고, 바로 복사해 쓸 템플릿과 stage·depth로 나눠 부르는 SKILL 초안을 붙였다.

### D1·D2에 없던 것 — 가져갈 것

| 요소 | 원문 위치 | 스킬에서 쓰는 방식 |
|---|---|---|
| 네 번째 라벨 `[미확인]` | 2장 공통 규칙 | 확인 전에는 결정 근거로 못 쓴다. 자료끼리 수치가 다르면 둘 다 `[미확인]` |
| 근거 무게 순서 | S2 판단 기준 | 직접 관찰한 행동 > 사용자 발언 > 2차 자료 > 디자이너 추정. 한 명 발언·사례 하나는 가설. 그렙은 인터뷰가 없어 대부분 아래 두 칸이라는 점을 스킬이 드러내게 한다 |
| 레퍼런스 두 번 보기 | 1장 | S1 전후 훑어보기는 패턴 가설용, 채택 판단은 문제 정의 뒤 S2에서. 카드 판정은 채택 / 변형 적용 / 참고만 / 제외 |
| 통제 수준 2×2 | S3-2 | 오류 영향(작음·큼) × 되돌리기(쉬움·어려움) → 자동 적용+실행 취소 / 미리보기 확인 / 제안만 / 사람 검토 필수·AI 미사용 검토 |
| 가치 정의문 | S3-3 | "…AI가 [역할]을 맡아 [개선]을 얻는다. AI가 틀리면 사용자는 [조치]를 할 수 있다." D2 문제 정의문과 짝 |
| 상태 16개 + "해당 없음(이유)" | S3-6, 템플릿 4 | D2 11개에 동의 필요·입력 부족·사용 불가·적용 후·긴 대기를 더함. **해당 없는 상태를 지우지 않고 이유를 남긴다** — D1 분석 때 본 ARC-005 규칙 9(처리 다시 시키기 없음)가 바로 이 경우 |
| 상태표 열 | 템플릿 4 | 문구 키 / 접근성 / 로그 이벤트 열 추가. 상태 → 수용 기준 → 측정 이벤트가 한 줄로 이어진다 |
| 답을 못 받으면 선택지별로 | 5장 SKILL | 차단형 질문이 미결이면 갈리는 부분을 선택지별로 나눠 쓴다. 하나로 확정하지 않음 |
| 질문 형식 | 5장 SKILL | 최대 5개, 질문마다 선택지 + "답이 없을 때 쓸 기본 가정" |
| stage · depth 입력 | 5장 SKILL | stage: all·S1~S6, depth: light·standard·full. 7장 규모(경량·표준·확장)와 짝. D2의 모드 4개와 합친다 |
| 단계 출력 끝 4줄 | 5장 산출물 형식 | ① 열린 질문 ② 새 가정 ③ 새 결정·결정 요청 ④ 다음 단계 진입 가능 여부와 이유 |
| AI 출력 가이드 | 3장 #9 | 모델 출력의 형식·길이·톤·금지 사항·좋은 예/나쁜 예. 그렙에는 [넘길 글 형식](handoff-format.md)이 이미 이 역할 |
| 흔한 설계 오류 12개 | 6장 | 리뷰 모드의 점검 목록으로 쓴다(채팅 기본값, 성공 화면만, 완벽한 결과로 테스트, 일괄 면책 문구 등) |
| 스킬 출력은 초안 | 7장 | `[사실]` 라벨이 실제 자료와 맞는지는 사람이 본다. 스킬 끝에 이 한 줄을 넣는다 |
