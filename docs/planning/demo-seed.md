- 작성일: 2026-11-25 (2026-11-26, 2026-11-27 고침)
- 상태: 데모 이야기(비개발 마케터의 캠페인 안), 데모 계정 둘, 시드 30건 이상은 **PO 결정(2026-11-26)**. 시드 자료 하나하나의 내용(가상 브랜드, 제목, 글, 날짜)은 AI가 제안했고 **PO가 확인했다(2026-11-26)**. 개발자가 시드를 넣어 개발 빌드에서 기대 결과를 실측한 뒤 데모 대본에 옮긴다
- 시드 파일: [`db/seed/demo/`](../../db/seed/demo/README.md)(2026-11-27). 파일·글·기사·미리 만든 요약은 4절 문구를 따라 **AI가 초안을 만들고 개발자가 확인**한다(개발자 결정 2026-11-27). 아래 7절 변경 기록 참고
- 근거: [기획서](PRD.md) 7절 데모 필수 범위·핵심 성공 기준과 12절("한국어 자료로 보여 준다"), [사용자 흐름도](user-flow.md) 11절, [넘길 글 형식](handoff-format.md), [명령어 설명서](commands.md)

발표(12/1)와 리허설(11/30), 개발 중 시험에 같이 쓰는 자료 묶음이다. 개발자가 검색·요약·같은 링크 판정을 시험할 때도 이 자료를 쓴다.

## 1. 데모 이야기

> 카페 브랜드 "솔밭커피"(가상)의 마케터. 개발은 모른다. 지난 6주 동안 인스타그램·스레드 레퍼런스 캡처, 트렌드 기사, 경쟁 카페의 캠페인 캡처, PDF 보고서를 그렙에 저장해 뒀다. 오늘 Claude에게 "겨울 텀블러 캠페인 안 써 줘"라고 하기 전에, 저장해 둔 자료 중 두 건을 골라 넘긴다.

- 주제를 "겨울 텀블러 캠페인" 하나로 모은다. 검색어는 마케터가 실제로 칠 낱말 `텀블러`, `캠페인`이다.
- 비슷한 낱말이 든 다른 자료(텀블러 세척 메모, 비품 주문 목록, 작년 캠페인 결과)를 섞는다. `찾기 텀블러`가 8건을 내고, `찾기 텀블러 캠페인`으로 4건까지 좁힌 뒤 2건을 고르는 장면을 만든다.
- 브랜드와 경쟁 카페("파란컵", "초록숲")는 모두 지어낸 이름이다. 실제 회사 자료는 쓰지 않는다(COM-002).

## 2. 넣는 원칙

1. **저장 날짜는 데모 당일(D) 기준 상대값으로 넣는다.** 리허설(11/30)과 발표(12/1)에서 `3주전`의 뜻이 바뀌므로, 시드 스크립트가 실행한 날을 D로 보고 `created_at`을 계산한다. 시드 날짜는 모두 다른 날로 둔다.
2. **요약은 데모 전에 모두 만들어 둔다.** 무대에서 기다리지 않게 한다. 단, 일부러 `blocked`로 둘 자료 하나(S33)는 그대로 둔다. 글자 없는 이미지 S07은 요약 없음(`(요약 없음: 이미지에 글자 없음)`)이 정상이다(2026-11-26 PO 결정).
3. **파일, 글, 링크 페이지는 팀이 직접 만든다.** 남의 문서·이미지를 화면에 띄우지 않는다(COM-002). 레퍼런스·경쟁 카페 캡처는 팀이 게시물 모양으로 그린 이미지다. 기사 링크는 팀이 무료 GitHub Pages(COM-005)에 올린 가상 기사 페이지이고, 페이지 맨 위에 `발표용 가상 기사`를 적는다. S33은 팀원 계정의 비공개 문서 링크라 로그인 없이는 열리지 않는다(개발자 결정 2026-11-27, 7절).
4. **수치는 예시임을 자료 안에 밝힌다.** 발표에서 실제 수치로 오해받지 않게 한다.
5. **검색 낱말을 자료마다 정해 둔다.** `텀블러`는 S07, S16, S21, S23, S25, S28, S30, S32에만, `캠페인`은 S02, S11, S23, S25, S28, S30에만, `회고`는 S11에만, `반값`은 S28 이미지 속 글자에만 넣는다. 나머지 자료에는 이 낱말을 쓰지 않는다.
6. **계정은 둘이다(PO 결정, 2026-11-26).** 로그인이 필수라(ACC-001) 데모 전용 계정을 쓴다.
   - 계정 A(GitHub): 자료 0건. 로그인과 처음 연 화면 장면에만 쓴다. 첫 화면의 `샘플 8건으로 해 보기`는 누르면 샘플이 실제 자료로 들어가 빈 계정이 깨지므로 데모에서 누르지 않는다.
   - 계정 B(Google): 시드 34건. 저장, 찾기, 고르기, 넘기기 장면에 쓴다.
   - 로그인 방식을 다르게 두면 전환이 `로그아웃` 뒤 `Google로 계속` 한 번이다.
7. **번호는 날짜 순서대로 받게 넣는다.** 자료 번호는 계정마다 1부터라(ARC-001) 가장 오래된 자료부터 넣는다. 그러면 S01이 1번, S34가 34번이 되고, 목록에서 번호와 저장 순서가 맞는다. 리허설 전에 실제 번호를 아래 장면표에 적는다.
8. **하루 AI 처리 상한(COM-005, 계정당 50건)을 넘기지 않는다.** 시드 34건과 무대 저장 1건이면 35건이다. 같은 날 같은 계정에 시드를 두 번 넣으면 넘으므로, 다시 넣을 때는 계정 B의 자료를 지운 새 계정을 쓰거나 다음 날 넣는다. 지운 번호는 다시 쓰지 않으므로(ARC-001) 같은 계정에 다시 넣으면 번호가 이어진다.
9. **붙여 넣는 글의 첫 줄이 제목이다.** 붙여 넣은 글의 제목은 첫 줄(24자까지)이다(넘길 글 형식 칸 규칙, 2026-11-26 PO 결정). 글 자료(S09, S11, S22, S24, S31, S32, S34)는 표의 제목을 첫 줄에 쓴다.

## 4. 팀이 만들 파일과 글

표에 내용을 적지 않은 자료는 제목에 맞게 짧게 만들되, 2절 5번의 낱말을 넣지 않는다.

## 6. 리허설 전 확인

- [ ] 계정 A가 자료 0건인지(휴지통 포함). 리허설에서 샘플 칩을 눌렀다면 완료 줄의 `버리기 <a>-<b>`로 치우고 휴지통도 비운다. 다음에 누르면 번호는 그 뒤부터 받는다(ARC-010)
- [ ] 계정 B의 상태줄이 `자료 34`이고, 번호가 S번호와 같은지
- [ ] `로그아웃` → `Google로 계속` 전환이 몇 초 걸리는지. 길면 계정 B를 미리 로그인해 둔 다른 브라우저 창으로 바꾼다
- [ ] 가상 기사 페이지(S06, S10, S14, S16, S20, S30)가 데모 당일에도 로그인 없이 열리는지
- [ ] S33 팀 공유 문서가 서버에서 실제로 `blocked`가 되는지. 본문이 받아지면 문서 공유 설정이 `제한됨`인지 확인한다
- [ ] 시드 34건의 요약이 모두 `ready`인지(S33, S07 제외. S07은 글자 없는 이미지라 요약 없음이 정상). docx·HEIC가 처리되지 않으면(COM-004 검토 중) 같은 내용의 PDF·JPEG로 바꾼다
- [ ] `찾기 텀블러`가 10건을 넘지 않는지, `찾기 텀블러 캠페인`이 4건인지. 요약 때문에 건수가 바뀌면 실측 칸과 대본을 고친다
- [ ] 핵심 성공 기준(기획서 7절): 팀원이 처음 쓰는 사람처럼 `도움말`만 보고 `찾기`부터 AI 도구 입력창에 붙여 넣기까지 1분 안인지 잰다
- [ ] 넘길 글을 Claude와 ChatGPT에 붙여 넣어 자료를 지시로 오해하지 않는지([넘길 글 형식](handoff-format.md) 7절)
- [ ] 화면 녹화(대비용)는 이 시드로 찍는다
- [ ] 무대 브라우저에서 리허설 뒤 `로그아웃`해 두었는지. 터미널 기록(COM-009)은 브라우저에 남아, 자료를 지우거나 새로고침해도 이전 출력이 그대로 보인다. 로그아웃하면 지워진다
