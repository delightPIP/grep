## 세 자료가 모두 같은 말을 한 것 (스킬의 고정 핵심)

셋이 따로 썼는데도 일치한 규칙이다. 스킬에서 예외 없이 지킨다.

1. 입력에 없는 요구사항·수치·API 필드·디자인 값·라이브러리를 만들지 않는다
2. 근거(문서명·위치)를 붙이고 사실·추론·가정을 나눈다
3. 필수 입력이 없으면 그 산출물만 멈추고 묻는다. 답에 따라 달라지지 않는 일은 계속한다
4. 미정은 미정으로 둔다. 답변 받음 ≠ 승인됨, 제출 ≠ 공개, 완료 조건 충족 ≠ 릴리스 승인
5. 실행하지 않은 테스트·빌드를 통과로 보고하지 않는다
6. 입력끼리 충돌하면 양쪽을 인용하고 어느 쪽도 고르지 않는다
7. 사람이 결정할 것(범위, 우선순위, 일정, 기술 채택, 병합, 릴리스, 장애 조치)은 제안으로만 낸다
8. 스킬마다 정상 / 정보 부족 / 입력 충돌 시나리오로 시험하고, 끝난 과거 작업에 읽기 전용으로 먼저 시범 적용한다

구조에서도 셋이 같은 결론이다: 큰 스킬 하나보다 작업별 작은 스킬과, 팀 정보를 한 곳에서 바꾸는 공용 파일.

## C1. 일반 지침(테크 리드 관점, '나중에 읽기')

### 한 줄 요지

결정과 증거의 연결을 줄이지 않는 것이 핵심이고, 파일 수는 줄여도 된다. 대표 이슈 하나에 원문·현재 단계·다음 행동·막힌 질문·원본 링크만 두고 명세 전문은 복사하지 않는다.

### 그대로 가져갈 것

| 요소 | 원문 위치 | 스킬에서 쓰는 방식 |
|---|---|---|
| 답이 없는 칸을 "없음"으로 읽지 않기 | 1단계 | `guardrails.md` 첫 규칙 옆에. "QA 담당을 안 적었다고 QA가 없다고 보지 않는다" 예시 포함 |
| 일부만 보류 | 2단계 머리 | 답에 따라 달라지는 작업만 보류하고 기존 동작 확인처럼 어느 답에도 필요한 일은 진행 |
| 되돌아갈 곳은 문제 종류로 | 2단계 1.1 | 기대가 다름 → 분석·질의, 코드가 다름 → 디버깅, 구버전 데이터를 못 읽음 → 기술 설계. 복귀 사유는 대표 이슈에 한 줄 |
| 질의서 한 항목 7칸 | 2단계 2.3 | 근거 / 질문 / 필요한 이유 / 미승인 기본안 / 지연 영향(보류할 작업·계속할 작업) / 답할 역할 / 상태 |
| 답이 오면 원본을 고친다 | 2단계 2.3 끝 | 정책은 기능 명세, 표현은 디자인 원본, 계약은 API 명세에 반영해야 질문을 닫는다 |
| 행동 단위로 먼저 자르기 | 2단계 2.4 | 기술 층보다 사용자 행동으로 먼저 나누고, 질문이 남은 항목은 요구사항으로 올리지 않는다 |
| 착수·완료 조건 4단 | 3단계 4.2 | 조사 착수 / 구현 착수(DoR) / 구현 완료(DoD) / 릴리스·운영 인계(DoD와 별도) |
| 가상 입력과 채운 문서 분리 | 4단계 4.4 | 예시 파일 첫머리에 F0~F7 입력 표, 이후 문서마다 근거 F-번호. 예시가 팀 규칙으로 굳는 것을 막는다 |
| 연결 검산 | 4단계 끝 | "Q-02 → REQ-03 → … → WEB-B"처럼 질문에서 릴리스까지 한 줄로 따라가 보는 점검 |
| 문서 대조 ≠ 시나리오 통과 ≠ 운영 승인 | 8단계 10.2 | 스킬 상태를 세 단계로 따로 적는다 |

## C3. 시니어 개발자 겸 테크 리드 관점('방해 금지 알림 스케줄')

### 한 줄 요지

공통 규칙 파일을 "헌법"으로 두고 6개 스킬이 모두 참조한다. 사람 확인 지점을 Gate 1~5로 나누고, 스킬별 시험 입력을 가장 구체적으로 썼다.

### 그대로 가져갈 것

| 요소 | 원문 위치 | 스킬에서 쓰는 방식 |
|---|---|---|
| 태그 4종 | 9-3 공통 규칙 3번 | `[사실]` `[추론]` `[가정]` `[제안]`. 출력에 그대로 붙인다 |
| Gate 1~5 | 10-2 | 지점마다 "사람이 눈으로 대조할 질문" 한 줄. `human-decisions.md`에 열로 추가 |
| 구체적 충돌 시나리오 | 9-4 | "PR 설명은 5개 제한, diff는 `>= 10`", "로그는 401, 사용자는 504라고 함", "회의록엔 담당 미정, 지시엔 발언자를 담당으로" 등. `scenarios.md`의 시험 입력으로 |
| 본문을 늘리지 않고 고치기 | 10-3 | 실패 사례는 SKILL.md가 아니라 체크리스트·규칙 파일에서 고친다 |
| 스킬 버전 규칙 | 10-3 | 출력 양식 변경 MAJOR, 점검 항목 추가 MINOR, 오타 PATCH |
| 시범 3단계 | 10-2 | 지난 작업으로 그림자 검증 → 저위험 스킬 1~2개 → 보정 후 확대. C1·C2의 시범 절차와 같은 방향 |

### C3에서 조심할 것

- 근거 없는 수치와 단정이 많다: "전역 상태 코드 70% 이상 감소", "압도적으로 유리", "PR 300줄 이하", "심사 버퍼 2~5일" 등. 가상 예시 안의 수치(사용자 18% 등)는 예시로 표시돼 있어 여기에 넣지 않는다.
- 스킬 본문에는 "입력에 없는 수치를 만들지 마라"고 쓰면서 가이드 본문이 그것을 어긴 셈이다.
- 그래서 C3에서는 구조와 시나리오만 가져오고, 수치는 가져오지 않는다. 필요한 값은 팀 설정의 빈칸으로 둔다.
