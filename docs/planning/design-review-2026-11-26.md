# 웹 화면 시안 디자이너 검토 (2026-11-26)

- 작성일: 2026-11-26
- 상태: PO 결정(2026-11-26) — 3절 다섯 항목을 "대조 의견"의 추천대로 반영했다([명령어 설명서](commands.md), [사용자 흐름도](user-flow.md), [기획서](PRD.md)). 같은 숫자 선택지가 있던 정책 ACC-002·ARC-003과 ARC-002 문구도 PO 승인으로 고쳤다. 4절 새 제안은 아직 고르지 않았다
- 대상: [그렙 웹 화면 시안](https://claude.ai/artifact/J6XT7UcSDvuPC2quoSsaRm) 7장(데스크톱 4장, 모바일 3장)
- 출처: PO가 받아 온 외부 디자이너 전문가 검토. 외부 검토는 첨언으로 보고 전부 받아들이지 않는다(AI 활용 로그 038과 같은 원칙. 이 작업의 로그는 041)

검토 항목 번호(A1, B2 …)는 원문을 따른다. A 공통, B 첫 화면(자료 0건), C 오류·설명·삭제·자동 완성, D 찾기 결과, E 직접 쳐 보기, F 모바일.

## 1. 대조 결과 요약

| 묶음 | 뜻 | 항목 |
|---|---|---|
| 가. 이미 정해져 있음, 시안만 고침 | 정책·설명서는 맞고 시안이 따르지 않았다. PO 결정 없이 시안과 데모 자료를 고친다 | A1(목록 번호), A2 일부(요약 없음 알림), B4(명령 개수), D3 일부(샘플 날짜), D4, F1 |
| 나. 기존 결정과 부딪힘 | 받아들이려면 정책이나 설명서의 결정을 바꿔야 한다. PO 결정이 필요하다 | C1, C2, B2, D3, A4 |
| 다. 새 제안 | 기존 결정이 없다. 받아들이면 설명서나 디자인 시스템에 새로 적는다 | A2 나머지, A3, B1, B3, D1, D2, D5, 걱정 4(글꼴 분리), 4절 ③(입력 받아 주기) |
| 라. 개발 확인 | 구현 방식이라 개발자가 정한다 | 한글 조합 중 엔터, 서버 응답 뒤 클립보드 복사, 자모 단위 자동 완성, 단축키 범위 |
| 마. 발표 현장 점검 | 디자인이 아니라 리허설 준비 | 프로젝터 대비·확대, 데모 링크 고르기, 비개발자 3~5명 5초 테스트 |

## 2. 가. 이미 정해져 있음 — 시안만 고침

| 항목 | 기존 결정 | 시안에서 고칠 것 |
|---|---|---|
| A1 목록 번호 | ARC-001: 목록 위치 번호를 쓰지 않고 자료 고유 번호만 쓴다. 번호 앞에 `#`을 붙이지 않는다 | 화면 3의 1~3 반복 번호, 모바일 칩 `#1`·`#3`을 고유 번호로. 데모 대본과 [데모 시드](demo-seed.md)도 같은 번호로 맞춘다. 진행(2026-11-26): 시안 캔버스 버전 24에서 칩 컴포넌트를 `종류 번호`로 바꿔 모바일 M3·M5와 웹 04의 칩은 고침. 남은 것: 웹 화면 3의 목록 번호, 디자인 시스템 "그렙 터미널"의 `Chip`(아직 `#`), 데모 대본·시드 |
| A2 요약 없음 알림 | [넘길 글 형식](handoff-format.md) 3절: 요약 없는 자료가 있으면 `! 요약 없음 1건` | 넘기기 결과 화면을 시안에 추가할 때 이 줄을 넣는다 |
| B4 명령 개수 | 설명서 2절: 13개(`설명` 포함) | 화면 1의 12줄 표를 설명서와 맞춘다 |
| D3 샘플 날짜 | 데모 시드 | `어제` 저장 자료가 최근 3건에서 빠진 것을 맞춘다 |
| D4 더 보기 | 설명서: 10건 초과 시 앞 10건과 전체 건수 | `23건 중 10건`인데 4행만 그린 것을 맞추고, 나머지를 보는 길을 그린다(아래 다. 참고) |
| F1 iOS 공유 대상 | ADR-IOS-009: 웹으로는 공유를 받을 수 없어 네이티브 공유 확장이 필요하다 | 없음. 검토자 지적과 같은 결론이다 |

## 3. 나. 기존 결정과 부딪힘 — PO 결정 필요

| 항목 | 지금 결정 | 검토 제안 | 대조 의견 |
|---|---|---|---|
| C1 삭제 확인 | 설명서 6절: `삭제? <제목> (되돌릴 수 없음)` 선택 `1 취소 · 2 삭제`. 되돌리기 유예는 공통 열린 질문(발표 뒤) | 숫자 선택지를 없애고 낱말로 확인(`버리기`를 다시 치면 실행). 더 좋게는 바로 지우고 `→ 되살리기` | ARC-001로 "숫자 = 자료 번호"가 됐으므로 숫자 선택지는 그 약속과 어긋난다. 같은 이유로 이어 쓰기 5건 초과 확인 `선택: 1 앞 10건만 · 2 N건 전부 · 3 취소`도 함께 바꿔야 한다. 되살리기는 열린 질문대로 발표 뒤로 두고 확인 방식만 바꾸는 안이 작다 |
| C2 `grep` 입력 | 설명서 1절 원칙 2·5절: 진짜 터미널 명령 이름은 쓰지 않고, `grep 결제`에는 `· grep 없음 → 찾기 결제`만 보여 준다 | 정식 이름은 두되 입력은 받아 실행(`· grep → 찾기로 실행`). `help`, `?`, `ls`도 | 원칙 2의 목적(진짜 명령으로 착각, 진짜 터미널에서 다른 명령 실행)은 "정식 이름"에 관한 것이라, 입력만 받아 주는 것은 원칙과 양립할 수 있다. 다만 받아 준 뒤 사용자가 진짜 터미널에서 `grep`을 칠 위험은 남는다 |
| B2 첫 화면 | 설명서: `도움말`(명령 13줄)은 자료가 없는 첫 화면에도 표시(US-6) | 첫 화면은 `담기·찾기·넘기기` 세 명령과 `[샘플 8건으로 해 보기]`, 나머지는 `도움말`로 | 자료 0건에서 예시 `찾기 결제`가 0건으로 끝나는 문제는 사실이다. 화면 4(샘플 8건)를 0건 사용자의 첫 화면으로 쓰자는 E1과 한 묶음으로 정하면 된다 |
| D3 0건 대체 | 설명서 6절: `· 0건: "검색어"` 뒤에 최근 저장 3건 | 낱말을 줄여 자동으로 다시 찾음(`· "온보딩"으로 1건`) | 최근 3건이 검색 결과처럼 읽힌다는 지적은 맞다. 자동 재검색은 검색 동작 정의가 바뀌는 것이라 개발 확인도 필요하다. 작은 안: 최근 3건을 유지하되 머리줄 `· 최근 저장 3건 (검색 결과 아님)`을 붙인다 |
| A4 표어 | 시안 표어 `저장 → 찾기 → 넘기기`, 명령은 `담기` | 표어를 `담기 → 찾기 → 넘기기`로, 확인 문구도 명령 동사로(`버릴까`), 모바일 주 버튼을 `넘기기 N건`으로 | 용어 사전에서 "저장"은 동작 이름이다. 표어를 명령으로 맞추면 명령 학습에는 좋다. 확인 문구는 설명서 6절 규칙("`동사?` + 대상")과 로그체를 지키면 `버리기? <제목>`이 된다(`버릴까`는 로그체가 아님). 모바일 `공유`는 [모바일·데스크톱 시안](design-mobile-desktop.md) 규칙 6(넘기기 기본은 OS 공유 시트)과 엮여 있다 |

| 항목 | 제안 | 적을 곳 |

| A2 넘기기 결과 | 건수, 포함된 자료 제목, 복사된 글 미리보기(펼치기), "AI 도구 입력창에 붙여 넣기" | 설명서 6절 넘기기 문구, 시안 새 화면 |

| B1 한 문장 소개 | 로고 아래 `저장해 둔 링크·캡처·PDF를 찾아 AI 도구에 붙여 넣을 글로 복사` | 시안 첫 화면, 데모 대본 |

| D4 더 보기 | `→ [더 보기]` | 설명서 `찾기`·`최근` |
| D5 꼬리표 | 진행 중은 회색 `·`, 문제는 `!`와 다음 행동(`→ 고치기 64`) | ARC-005 사용자 문구, 설명서 6절 |

## 5. 라. 개발 확인 — 개발자가 정함

구현 방식은 개발 안을 기본으로 한다. 아래는 개발자에게 넘길 확인 목록이다.

1. 한글 조합 중 엔터: 명령이 두 번 실행되거나 마지막 글자가 남지 않는지(데모 장비)
2. 서버 응답을 기다린 뒤의 클립보드 복사: 브라우저(특히 Safari)가 거부하는지. 이어 쓰기 `찾기 결제 | 넘기기`를 데모 브라우저에서 확인하고 실패 화면 준비
3. 한글 자동 완성: 글자 단위가 아니라 자모 단위로 비교(`골` → `고르기`)
4. 단축키 범위: Ctrl+C·Ctrl+L은 Windows에서 복사·주소창과 겹친다

## 6. 마. 발표 현장 점검

1. 프로젝터에서 회색 보조 글자가 보이는지, 밝은 테마와 125~150% 확대 준비. 회색 글자 대비 4.5:1 측정
2. 데모 링크는 본문을 확실히 가져오는 문서로(SNS 링크는 본문 못 가져옴이 날 수 있음)
3. 방금 저장한 링크는 요약 생성 중일 수 있다. 데모가 "저장 후 바로 넘기기"면 넘길 글에 `(요약 없음: 아직 만드는 중)`이 들어간다(넘길 글 형식 3절). 데모 순서를 기다렸다 넘기기로 짤지 정한다
4. 비개발자 3~5명에게 첫 화면을 5초 보여 주고 "무엇을 하는 서비스 같은가" 묻기(인터뷰가 아니라 리허설용 확인)

## 7. 검토자 원문

검토자가 데모 전에 꼭 고칠 것으로 꼽은 순서: 1) 번호 체계 통일(A1) 2) 넘기기·고르기 결과 화면(A2, D2) 3) 첫 화면(B1, B2, B3) 4) 목록 행(D1) 5) 다음 명령 칩(A3) 6) 실기 점검. 미뤄도 된다고 본 것: 삭제 확인과 되살리기(C1, 데모에서 버리기를 시연하지 않을 때만), `grep` 받아 주기(C2, 청중이 직접 쳐 보지 않을 때만), 입력 보조, 글꼴 분리, 검색 보완(D3~D5), 용어 통일(A4), 창 점(A5), 두더지(E2), 기호 잔손질(C5), 모바일 전부(F1~F4).

컨셉 의견: 터미널 외형은 크게 불리하지 않고, 불리해지는 조건은 명령 입력이 유일한 조작 수단일 때다. 명령은 가장 빠른 길로 두되 유일한 길로 만들지 말라. 데모의 주 대상은 "AI 도구를 자주 쓰는 비개발자"로 정하는 편이 일관된다(검토자 추측).

나머지 항목(A5 창 점, C3~C5, E2, F2~F4)은 시안 다듬기라 PO 결정 없이 시안 수정 때 반영한다.
