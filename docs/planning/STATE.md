# 기획 상태 문서

서비스 기획의 단일 기준 문서다. 결정이 생길 때마다 갱신한다. "(가설)"로 표시한 항목은 대상 사용자에게서 인터뷰나 직접 근거로 확인되지 않은 것이다.

## 0. 메타

- 프로젝트명: grep (저장소 이름)
- 서비스 이름: 그렙(영문 grep). 팀 이름: Unwrap("문제를 풀어 보다"). 2026-11-25 PO 결정(12절). 영문 표기 grep은 AI가 저장소 이름에 맞춰 적은 것(AI 로그 018)을 2026-11-26 PO가 확정했다
- 팀: 박기석(개발자), 김태인(PO)
- 기획 목적: 실제 출시할 서비스
- 대상 도메인: 개인 자료 아카이브·AI 연결, 멀티플랫폼(Android, iOS, Web, Windows)
- 고정된 솔루션(PO 결정, 12절): 여러 플랫폼에서 파일과 자료를 자유롭게 저장해 아카이브에 모으고, 나중에 AI 도구가 쓸 수 있게 요약해 넘겨준다. 문제 정의는 이 솔루션에 맞춘다
- 첫 검증 대상: AI 활용자(개발자 포함). 2026-11-25에 개발자에서 넓힘(12절). 개발자는 그 안의 숙련 사용자로 본다
- 컨셉(PO 결정, 12절): 터미널 느낌의 화면과 쉬운 명령어 몇 개로, 개발자가 된 듯한 경험으로 자료를 아카이브에 모은다
- 결과물 위치: 이 저장소 `docs/`
- 진행 모드: 최고 성능 모드(근거 수집 6갈래, 검증 6묶음 48건, 비평 3회 후 수정)
- 현재 단계: 1단계 문제 프레이밍 범위 확정 완료(대상은 AI 활용자, 개발자 포함). 4단계 경쟁 조사와 포지셔닝 확정 완료(9절). PO 요청으로 [기획서](PRD.md)와 [디자인 레퍼런스](design-references.md)를 먼저 만들었다. 기획서 0.3에 PO 판단을 반영했고(12절), 범위·첫 플랫폼·도입 기술은 개발자가 기술 명세를 확인하며 정한다. 가설 검증 설문은 12명 응답으로 마감하고 분석했으며([설문 결과](survey-results.md)) 이전 문제 정의 기준이다. 페르소나 초안은 이전 문제 정의 기준이라 다시 써야 한다(10절). 인터뷰와 일지 연구는 하지 않고, 범위는 발표(2026-12-01)까지다(12절)
- 마지막 갱신: 2026-11-25
- 요약: 개발자·외부 공유용 한 장 요약은 [기획 한눈에 보기](overview.md)

## 1. 문제 질문

- 질문: 왜 작업 레퍼런스를 저장해 두는 AI 활용자는, AI 도구로 작업할 때 저장해 둔 자료를 한 번에 모아 넘기지 못하고, 자료 없이 묻거나 하나씩 다시 넣는가?
- 부제: → 자료는 여러 저장 수단에 흩어져 있고, AI 도구는 사용자가 그때 넣어 준 자료만 읽는다는 관점 (가설. 원인은 열어 두고 2단계에서 검증)
- 이전 질문(2026-11-24 교체): "왜 업무 레퍼런스를 저장해 두는 프로덕트 메이커는, 그 자료가 필요할 때 다시 찾아 쓰지 못하는가?" 솔루션이 "아카이브·AI 연결"로 고정되면서(12절) 다시 찾기 실패는 문제 자체에서 원인 후보 N2로 내렸다(6절).

## 2. 문제정의 4요소

| 요소 | 문장 | 연결 근거 ID | 근거 상태 |
|---|---|---|---|
| 누가 | 작업 레퍼런스를 2개 이상의 저장 수단에 나눠 저장하고, 주 1회 이상 새로 저장하며, 최근 4주 안에 AI 도구로 주 3회 이상 AI 작업(회사 업무든 개인 프로젝트든)을 하고 그러면서 저장해 둔 자료를 넣으려 한 적이 있는 사람(AI 활용자). 직군은 묻지 않으며 개발자를 포함한다. 팀 협업 도구에만 저장하는 사람은 제외 | E-05, E-06, E-19 | 부분. 근거는 "여러 저장 수단에 나눠 저장한다"만 뒷받침한다: E-05는 해외 2004년 214명, E-06은 국내 비표본, E-19는 해외 기술기업 36명(PM·디자이너·엔지니어가 섞여 있어 개발자만의 수치가 아님). "AI 도구에 저장해 둔 자료를 넣으려 한다"는 근거 없음(13절 공백 9). "AI 도구로 주 3회 이상 작업한다"는 AI 활용자를 가르는 스크리너용 가정이며 근거 없음(13절 공백 15). 기준값(2개, 주 1회, 주 3회, 4주)은 모두 스크리너용 가정 |
| 어떤 상황에서 | AI 도구로 작업(코드 작성, 문서 작성, 조사 정리 등)을 하다가, 저장해 둔 자료를 그 작업의 재료로 넣어야 할 때 | 없음 | 근거 없음(13절 공백 9) |
| 무엇을 못 해서 | (가설) 여러 저장 수단에 흩어진 자료를, AI 도구가 읽을 수 있는 형태로 모아 넘기지 못해서. 왜 못 넘기는지(원인)는 6절 후보로 열어 둔다 | E-19, E-42 (간접, 원인 후보 N2에만 해당) | 근거 약함. 확보한 근거는 "저장한 자료를 다시 찾기 어렵다"까지만 말한다(E-19 해외 36명, E-42 영국 51~52명 자기보고). 넘기기 자체를 다룬 근거는 없음(13절 공백 10) |
| 어떤 손해 | (가설) 자료를 하나씩 다시 찾아 붙여 넣거나 올리는 데 시간을 쓰고, 그 수고를 피하려고 자료 없이 AI 도구에 묻고, 결과물에 저장한 자료가 반영되지 않아, 저장한 자료가 작업에 쓰이지 않는다 | 없음 | 근거 없음(13절 공백 11). 붙여 넣기·올리기가 수고가 아니라 충분한 방법일 수 있다는 대안 해석 있음(5-1 반증 조건 2) |

손해를 지표로 바꾼 후보:

| 대상 | 지표 후보 | 측정 방법 |
|---|---|---|
| 원인 | 넘기지 못한 이유의 분포. 분류 범주: 자료가 여러 저장 수단에 흩어져 있음 / 넘길 자료를 다시 찾지 못함 / AI 도구가 읽지 못하는 형식 / 양이 많아 무엇을 넣을지 고르지 못함 / 대화·도구가 바뀌어 다시 넣어야 함 / 회사 자료라 넣기 꺼려짐 / 넣을 필요를 못 느낌 | 인터뷰에서 최근 AI 작업 중 자료를 넣은 사례와 넣지 못한(넣지 않은) 사례를 각각 1건 이상 받아 분류 |
| 손해: 넘기는 수고 | AI 작업 한 번에 자료를 넣으려고 붙여 넣기·올리기를 한 횟수와 쓴 시간 | 1~2주 일지(AI 작업마다 기록) |
| 손해: 자료 없이 질문 | 저장해 둔 관련 자료가 있었는데도 넣지 않고 AI 도구에 물은 작업의 비율 | 일지(작업마다 "관련 자료를 저장해 둔 게 있었는가, 넣었는가" 기록) |
| 손해: 다시 넣기 | 같은 자료를 다른 대화나 다른 AI 도구에 다시 넣은 횟수(주당) | 일지 |
| 손해: 작업에 쓰이지 않음 | 작업에 필요했던 자료 중 저장해 두었는데도 결과물에 반영하지 못한 비율 | 일지 + 인터뷰 확인 |

## 3. 한 문장 정의

- 현재 문장: 작업 레퍼런스를 저장해 두는 AI 활용자는, / AI 도구로 작업하다가 저장해 둔 자료를 재료로 넣어야 할 때 / 그 자료를 AI 도구에 넘겨 쓰려고 하지만, / 흩어진 자료를 AI 도구가 읽을 수 있는 형태로 모아 넘기지 못해(가설), / 자료 없이 묻거나 하나씩 다시 넣게 되고 저장한 자료를 작업에 쓰지 못한다(가설).
- 상태: '관찰한 장애'와 손해 모두 가설이다. 인터뷰로 확인되지 않았고 문헌 근거도 없다(13절 공백 9·10·11). 장애의 원인은 6절에서 다룬다.

## 4. 용어 사전

| 용어 | 정의 | 쓰지 않을 표현 |
|---|---|---|
| 자료 | 사용자가 나중에 쓰려고 저장하는 링크·파일·논문·영상·이미지 등 모든 대상 | 미디어, 콘텐츠, 아이템 |
| 작업 레퍼런스 | 자료 가운데 AI 작업에 쓰려고 저장한 것. 회사 업무용과 개인 프로젝트용을 모두 포함한다. 둘을 구분해 말할 때는 "회사 업무용", "개인 프로젝트용"으로 쓴다 | 업무 레퍼런스, 개발 레퍼런스(이전 용어), 레퍼런스 자료, 참고 자료(혼용 금지) |
| AI 활용자 | AI 도구로 주 3회 이상 AI 작업을 하는 사람. 직군과 무관하며 개발자를 포함한다. 기준 횟수는 스크리너용 가정이다 | AI 네이티브, 파워 유저, 바이브 코더 |
| 저장 | 자료를 어딘가에 넣어 두는 한 번의 동작. 분류는 포함하지 않는다 | 아카이빙·아카이브(동작을 말할 때), 스크랩, 클리핑 |
| 저장 수단 | 자료를 넣어 두는 개인용 앱·기능(브라우저 북마크, 메신저 나에게 보내기, 나중에 읽기 앱, 개인 노트 앱, 레퍼런스 전용 앱, 사진첩, 컴퓨터 폴더 등). 팀 공용 공간과 열어 둔 브라우저 탭은 넣지 않는다 | 저장소(아카이브와 혼동) |
| 아카이브 | 서비스 안에서 저장된 자료가 모이는 곳 | 보관함, 서랍 |
| 분류 | 자료에 폴더나 태그를 정해 붙이는 일 | 정리(분류를 뜻할 때), 카테고라이징 |
| 태그 | 자료에 붙는 분류 꼬리표. 자동·수동 모두 포함 | 라벨, 카테고리, 해시태그 |
| 맥락 정보 | 저장물에 남는 저장 당시의 정보: 출처, 저장 시점, 조사 주제·목적 | 메타데이터(사용자 대상 문서에서) |
| 단서 | 다시 찾을 때 사람이 떠올리는 정보(무슨 조사 중이었는지, 대략 언제, 어느 사이트 등) | 힌트, 키워드(검색어와 혼동) |
| 검색어 | 검색창에 입력하는 단어 | 키워드 |
| 다시 찾기 | 예전에 저장한 자료를 필요할 때 찾아내는 일 | 재검색(웹 검색과 혼동), 리파인딩, 걸러 찾기 |
| 다시 쓰기 | 찾아낸 자료를 실제 작업에 활용하는 일 | 재방문(열람만 뜻하므로) |
| 재방문 | 저장한 자료를 다시 여는 일. 다시 쓰기와 구분한다 | — |
| 조사 세션 | 한 주제를 알아보려고 연속해서 탐색·저장하는 시간 묶음 | 리서치, 래빗홀 |
| AI 도구 | 사용자가 말로 일을 시키는 AI 서비스·프로그램(대화형 AI, AI 코딩 도구 등). 서비스 밖의 것을 가리킨다 | 챗봇, LLM, 에이전트(사용자 대상 문서에서) |
| AI 작업 | AI 도구에 시켜서 작업 결과물(코드, 문서, 기획안 등)을 만드는 일 | 프롬프팅, 바이브 코딩 |
| 넘기기 | 저장해 둔 자료를 AI 도구가 읽을 수 있게 전달하는 일. 붙여 넣기, 파일 올리기, 연결을 통한 전달을 모두 포함한다 | 공급, 주입, 컨텍스트 제공 |
| 요약 | 그렙이 자료의 내용을 AI 도구에 넘기기 좋게 줄인 글 | 서머리, 다이제스트 |
| 연결 | AI 도구가 서비스 아카이브의 자료를 직접 읽도록 이어 두는 것(MCP 등) | 연동, 통합, 플러그인(방식을 특정하지 않을 때) |
| 묶음 | 사용자가 넘기려고 고른 자료의 모음 (기획서에서 제안, PO 확인 전) | 자료 묶음, 컬렉션, 세트 |
| 넘길 글 | 묶음을 AI 도구에 붙여 넣을 수 있게 만든 글. 기본 내용은 자료마다 제목, 출처, 저장 시각, 요약 (기획서에서 제안, PO 확인 전) | 붙여 넣을 글, 프롬프트, 컨텍스트 |
| 본문 | 저장한 자료의 원래 내용 전체. 요약과 구분한다 | 원문(혼용 금지) |
| 터미널 화면 | "터미널 느낌의 화면"의 줄임말. 터미널처럼 보이고 움직이는 그렙의 화면이며 진짜 명령줄 도구가 아니다 | CLI, 콘솔, 셸 |

## 5. 범위 규칙

- 포함: 개인이 작업 레퍼런스를 저장하는 순간부터, 그 자료를 AI 도구에 넘겨 AI 작업에 쓰는 순간까지. 다시 찾기는 넘기기의 앞 단계로 포함한다
- 포함 대상: AI 활용자(개발자 포함). 직군으로 가르지 않는다. 개발자와 비개발자의 차이는 이번 범위에서 확인하지 않는다(12절)
- 포함 용도: 회사 업무용과 개인 사이드 프로젝트용 개발 자료 모두(12절)
- 포함 자료 형식: 링크, 이미지·스크린샷, 문서·논문 PDF, 영상, 로컬 파일 등 모든 형식
- 제외: 팀 협업 문서 관리, 조직 내부 정보 검색, 클라우드 백업 자체, 소셜미디어 여가 저장(인스타 저장 등은 저장 수단으로만 다룸)
- 제외(AI 관련): AI 도구가 하는 일 자체(답변 생성, 대화, 코드 작성). 그렙은 AI 도구와 경쟁하지 않고 자료를 넘기는 쪽에 선다. 조직 지식베이스를 AI로 검색하는 일도 제외한다
- 근거 분포 주의(AI): 7절의 근거는 모두 저장과 다시 찾기에 관한 것이다. AI 도구에 자료를 넘기는 행동을 다룬 근거는 한 건도 없다(13절 공백 9~11)
- 근거 분포 주의: 확보한 근거는 웹 링크·북마크·이메일·PC 파일에 몰려 있고, 논문 PDF·영상은 거의 없다. 형식별 차이는 설문의 저장 형식 문항으로만 본다(13절 공백 5).
- 일반화 금지 예시:
  - 다시 찾기 근거(E-19, E-42 등)로 "AI 도구에 자료를 넘기지 못한다"를 말하지 않는다. "다시 찾기에서는 ~였다"로 쓰고 원인 후보 N2에만 붙인다.
  - 북마크 연구(E-01)로 논문·영상·파일 전체의 다시 찾기를 말하지 않는다.
  - 이메일·PC 파일 분류 연구(E-09, E-10, E-11)로 링크 저장 행동을 단정하지 않는다. "이메일에서는 ~였다"로 쓴다.
  - 디지털 호딩 연구(E-13, E-14)는 일반 대상 상관연구다. 손해 근거로 쓰지 않는다. 부담감은 설문 E2로만 본다.
  - 재방문(열람) 수치로 다시 쓰기를 말하지 않는다.
  - "저장한 글의 82%는 읽지 않는다"는 출처가 없다(E-07). 쓰지 않는다.

## 5-1. 반례와 반증 조건

| 반례 페르소나 (가상) | 근거 | 이 사람에게 문제가 약한 이유 |
|---|---|---|
| 자료 없이도 충분한 사람: AI 도구의 웹 검색과 자체 지식만으로 작업을 끝낸다 | 근거 없음(가정) | 저장해 둔 자료를 넣을 필요를 느끼지 않음 |
| 붙여 넣기로 충분한 사람: 필요한 자료 한두 개를 바로 찾아 붙여 넣는다 | E-05(해외 2004년 12명 과제에서 시행의 93%가 첫 방법으로 성공), E-19(해외 36명 중 52%가 다시 찾기 전략이 자주 통한다고 응답). 둘 다 다시 찾기까지만 해당 | 넘기는 수고를 손해로 느끼지 않음 |
| AI 도구 안에 이미 모아 둔 사람: AI 도구의 자체 자료 기능(파일 올리기, 프로젝트, 연결 기능 등)에 자료를 넣어 두고 쓴다 | 이런 사람이 얼마나 되는지는 근거 없음(가정). 기능은 있다: ChatGPT·Claude 프로젝트, Copilot Spaces 등([경쟁 서비스 조사](competitors.md) 간접 경쟁 1) | 별도 아카이브가 필요 없음 |
| 저장을 안심용으로 하는 사람: 다시 쓸 생각보다 "나중에 못 찾을까 봐" 저장한다 | E-04(26/35가 미래 쓸모 때문에 저장, 일부는 거의 안 보지만 못 지움) | 저장한 자료가 작업에 쓰이지 않는 것을 손해로 느끼지 않을 수 있음 |

문제 자체에 대한 반증 조건 (원래 인터뷰 8~12명 기준으로 썼다. 인터뷰는 하지 않기로 해(12절), 추가 설문도 하지 않으므로 네 조건 모두 이번 범위에서 판정하지 않는다). 솔루션은 고정이므로, 조건에 걸리면 솔루션을 바꾸지 않고 대상·상황·손해 문장을 다시 쓴다:

1. 응답자의 2/3 이상이 최근 4주 동안 AI 작업에 저장해 둔 자료를 넣을 필요가 없었다고 답한다. 이 경우 '누가'와 '상황'을 다시 쓴다(대상 집단이나 작업 종류를 좁힌다).
2. (손해) 자료를 넣은 사례의 과반에서 붙여 넣기·올리기가 한두 번으로 끝났고 응답자가 불편으로 꼽지 않는다. 이 경우 "넘기는 수고"를 손해 문장에서 뺀다.
3. 응답자의 과반이 AI 도구의 자체 자료 기능에 자료를 모아 두고 쓰며 따로 저장해 둔 자료를 넣을 일이 없다고 답한다. 이 경우 경쟁 범위와 포지셔닝(4단계)을 다시 본다.
4. (손해) 일지에서 "관련 자료를 저장해 두었는데 넣지 않고 물은" 작업이 소수다. 이 경우 "자료 없이 질문"을 손해 문장에서 뺀다.

원인 후보 N2(넘길 자료를 다시 찾지 못함)에 대한 조건. 이전 문제 정의의 반증 조건이었고, 지금은 N2가 주된 원인인지 가르는 데 쓴다:

- N2-1. 응답자의 2/3 이상이 저장한 자료를 검색으로 문제없이 찾는다고 답한다. (E-19 해외 36명에서는 52%가 다시 찾기 전략이 자주 통한다고 답했다.)
- N2-2. 다시 찾기 실패보다 "저장한 걸 아예 잊는다"가 과반에서 주된 문제로 나온다. 스크리너가 최근에 자료를 쓰려 한 사람만 뽑으므로 이 집단은 구조적으로 걸러진다. 스크리너 탈락자 비율을 따로 기록한다.
- N2-3. 일지에서 웹 다시 검색의 과반이 저장 수단을 먼저 찾아보지 않고 처음부터 일어났다. 이 경우 웹 다시 검색은 다시 찾기 실패의 결과가 아니라 평소 습관으로 본다.

원인 후보별 반증 조건은 6절에 둔다.

## 9. 경쟁 서비스

공개 자료 기준이며 직접 사용 확인은 하지 않았다. 상세 표는 [경쟁 서비스 조사](competitors.md)에 둔다. 4단계에서 포지셔닝을 확정한다.

- 2026-11-25에 새 경쟁 범위로 다시 조사했다: 자료·기억을 여러 AI 도구에 넘겨주는 서비스 8곳, AI 도구 7종의 자체 자료 기능, 저장 수단 16곳의 AI 도구 연결, 국내 6곳. 핵심 사실 46건을 원문과 대조했고 불일치는 없었다(부분 일치는 교정해 반영).
- 관찰(가설): AI 도구에 연결하는 것(MCP) 자체는 이미 흔해 차별점이 되기 어렵다. "저장해 두고 여러 AI 도구에 넘긴다"는 조합도 해외에 있다(Supermemory, MyMemory). 공개 자료에서 찾지 못한 것은 국내 서비스, 국내 저장 수단에서 가져오기, 개발자를 대상으로 한 "직접 고른 자료의 저장 + AI 도구 연결"이다.
- 포지셔닝(2026-11-25 PO 확정, 효과는 검증 전):
  - 차별점 문장: AI가 알아서 찾아 읽는 연결형 서비스와 달리, 그렙은 사용자가 명령어로 자료를 직접 골라 묶어 어떤 AI 도구에든 넘기게 해서, 흩어짐(N1)과 매번 다시 넣기(N5)를 해결한다.
  - 첫 시장: 국내 AI 활용자, 한국어. 차별점이 아니라 시작하는 곳이다.
  - 넘기는 형태: 작업에 맞게 요약해 넘긴다(고정된 솔루션). 차별점으로 내세우지 않는다.
  - 넘기는 방식의 순서: AI 도구에 붙여 넣을 글을 만들어 주는 방식을 앞에 두고, 연결(MCP)을 함께 둔다. 사용자 정의 연결은 AI 도구의 요금제에 따라 막혀 있다(ChatGPT는 전체 기능이 Business 이상, Claude 무료는 1개. [경쟁 서비스 조사](competitors.md) E-49, E-50).
  - 겹치는 서비스: Supermemory와 MemoryPlugin의 브라우저 확장이 AI 도구 입력창에 저장된 맥락을 끼워 넣는다(E-71, E-77). 실제 차이는 직접 써서 확인한다(13절 공백 17).
- 포지셔닝 원칙(PO 결정): AI 도구와 경쟁하지 않는다. 연결(MCP)로 AI 도구에 붙거나, AI 도구에 넣을 글을 쓰기 쉽게 돕는 방식으로 함께 쓰인다.

## 10. 사용자 리서치

- [설문 결과](survey-result.md)(2026-11-25, 응답 8개 중간 집계, E-92): 모든 칸이 5건 미만이라 판정은 보류. 첫 신호로 8명 중 5명이 지난 4주에 저장한 걸 모르고 다시 찾거나 다시 저장했고(N7 쪽), 검색으로 바로 찾는다는 사람은 1명(디자이너)뿐이었다.
- 가설 검증 설문은 2026-11-25에 12명 응답으로 마감했다. 인터뷰 참여 희망자는 없었고 인터뷰는 하지 않는다. 집계와 실패 사례 분석은 [설문 결과(12명)](survey-results.md)에 있다. 이전 문제 정의 기준이라 AI 작업은 묻지 않았다. 원인 후보 N2의 반증 조건 N2-1(검색으로 문제없이 찾음)과 N2-3(웹 다시 검색이 습관)은 충족되지 않아 N2를 원인 후보로 유지한다. E-92와 기획서·저니맵·한눈에 보기의 설문 숫자는 12명 기준으로 고쳤다.

- [사용자 저니맵](journey-map.md) 초안(2026-11-25): PO가 서술한 사용자(SNS, 유튜브, 웹 등에서 이것저것 저장하지만 AI 작업할 때 떠올리지 못하고 같은 질문·검색을 반복)를 주인공으로, 비교 1명과 반례 1명을 같은 7단계로 그렸다. 새 원인 후보 N7(떠올리지 못함)과 결정적 순간 M1~M4, 기능 후보 F20·F21을 제안했다(PO 판단 전). 발표용 슬라이드도 같은 내용으로 만들었다.

5단계 산출물을 일부 앞당겨 [페르소나 초안](personas.md)을 만들었다(대상 7명, 반례 4명, 스크리너 초안). 모두 가상 인물이다. 인터뷰는 하지 않기로 해(12절) 인터뷰 가이드는 만들지 않는다.

- 다시 쓰기 필요: 지금 페르소나와 스크리너는 이전 문제 정의 기준이다. 장면에 AI 작업이 없고, 스크리너에 AI 도구 사용 문항이 없다. 원인 후보 N1~N6에 맞춰 고친다. 기존 인물은 N2 하위 원인(A~H)용으로 남길 수 있다.

## 11. 해결·지표

- 해결 방향 한 문장 (PO 결정으로 고정, 효과는 검증 전): 여러 플랫폼에서 파일과 자료를 자유롭게 저장해 아카이브에 모으고, 나중에 AI 도구가 쓸 수 있게 요약해 넘겨준다.
- 컨셉 (PO 결정, 효과는 검증 전): 터미널 느낌의 화면과 쉬운 명령어 몇 개로, 개발자가 된 듯한 경험으로 자료를 아카이브에 모으고 꺼낸다. 진짜 명령줄 도구가 아니라 터미널처럼 보이고 움직이는 화면이다. 개발자에게는 익숙한 방식, 비개발자 AI 활용자에게는 개발자가 된 듯한 경험을 노린다.
- 컨셉의 위치: 컨셉은 경험과 인상의 차별점이다. 기능의 차별점(포지셔닝, [경쟁 서비스 조사](competitors.md)의 차별점 문장 후보)은 따로 정한다. 조사한 경쟁 서비스의 화면 형태는 확인하지 않았다(직접 사용 확인 항목).
- 컨셉에서 생긴 설계 질문(7단계에서 다룸, 모두 근거 없음):
  - 저장하는 순간은 공유 한 번으로 끝나야 하는데 명령어 입력과 어떻게 함께 둘지. 가설: 저장은 공유·붙여 넣기로 하고, 터미널 화면은 찾아서 AI 도구에 넘기는 쪽에 둔다.
  - 휴대폰(Android, iOS)에서 명령어를 치는 부담을 어떻게 줄일지.
  - 명령어를 몇 개로, 얼마나 쉽게 둘지. 비개발자가 처음 봤을 때 겁내지 않는 수준이 어디인지(13절 공백 15).
- 넘기는 방식 후보(7단계에서 정함): 연결(MCP)로 AI 도구가 아카이브를 직접 읽게 하는 방식, AI 도구에 넣을 글을 자료와 함께 만들어 주는 방식.
- 자동 태그의 위치: 사용자에게 내세우는 기능이 아니라 요약·넘기기를 위한 내부 재료로 둔다. 이메일·PC 파일에서는 태그로 찾을 때 성공률이 낮고 느렸다(E-11)는 근거와도 어긋나지 않는다.
- 이전 해결 방향(2026-11-24 교체): "쉽고 빠르게 저장하면 태그와 맥락 정보가 자동으로 붙어, 나중에 한 번에 다시 찾을 수 있게 한다."
- 7단계에서 다룰 연결 문제: 요약해서 넘기면 원문보다 정보가 줄어든다. 사용자가 요약을 믿고 쓰는지, 원문이 필요한 작업이 얼마나 되는지 근거가 없다(13절 공백 13). 회사 업무 자료를 AI 도구에 넘기는 데 대한 제약도 확인하지 않았다(원인 후보 N6).
- 설계 단서(가설): 자동 분류는 사용자가 승인·수정할 수 있을 때 수용성이 높을 수 있다(E-23, E-24 간접).
- 설계 단서(가설): 화면 기록을 타임랩스로 보여 주면 웹 페이지 다시 찾기가 빨라졌다(E-37, 대학생 20명 실험). 라이프로그 사례 연구 1건에서는 맥락 기반 기능이 기대만큼 자주 쓰이지 않았지만 쓰였을 때는 다시 찾기 효과를 높였다(E-39). 인과 맥락 기반 파일 검색은 결과 평가가 평균 17% 높았지만 "쉽게 찾는다"는 자기 평가에는 차이가 없었고 실제 찾기 시간은 측정하지 않았다(E-38). 맥락 정보는 사용자 입력 없이 남고, 다시 찾는 화면에서 자연스럽게 보여야 할 수 있다.
