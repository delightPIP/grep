# 기획 상태 문서

grep 기획의 단일 기준 문서다. 결정이 생길 때마다 갱신한다. "(가설)"로 표시한 항목은 대상 사용자에게서 인터뷰나 직접 근거로 확인되지 않은 것이다.

## 0. 메타

- 프로젝트명: grep
- 팀: 박기석(개발자), 김태인(PO)
- 기획 목적: 실제 출시할 서비스
- 대상 도메인: 개인 자료 아카이브·자동 태깅, 멀티플랫폼(Android, iOS, Web, Windows)
- 첫 검증 대상: 팀과 비슷한 프로덕트 메이커(개발자·PO·디자이너)
- 결과물 위치: 이 저장소 `docs/`
- 진행 모드: 최고 성능 모드(근거 수집 6갈래, 검증 6묶음 48건, 비평 3회 후 수정)
- 현재 단계: 1단계 문제 프레이밍 범위 확정 완료, 페르소나 초안 작성 중(5단계 일부를 앞당김)
- 마지막 갱신: 2026-11-24

## 1. 문제 질문

- 질문: 왜 업무 레퍼런스를 저장해 두는 프로덕트 메이커는, 그 자료가 필요할 때 다시 찾아 쓰지 못하는가?
- 부제: → 저장은 한 번의 동작으로 쉬워졌지만, 다시 찾기는 여전히 사람이 떠올리는 단서에 기대고 있다는 관점 (원인은 열어 두고 2단계에서 검증)

## 2. 문제정의 4요소

| 요소 | 문장 | 연결 근거 ID | 근거 상태 |
|---|---|---|---|
| 누가 | 업무 레퍼런스를 2개 이상의 저장 수단에 나눠 저장하고, 주 1회 이상 새로 저장하며, 최근 4주 안에 저장한 자료를 다시 찾으려 한 적이 있는 프로덕트 메이커(개발자·PO·디자이너). 팀 협업 도구에만 저장하는 사람은 제외 | E-05, E-06, E-19 | 부분. E-05는 해외 2004년 214명(주 1회 이상 평균 약 5가지 보관 방법), E-06은 국내 비표본, E-19는 해외 기술기업 36명. 국내 정량은 없음(13절 공백 4). 기준값(2개, 주 1회, 4주)은 스크리너용 가정 |
| 어떤 상황에서 | 저장해 둔 자료를 작업에 쓰려고 다시 찾을 때 | E-19, E-01 | 부분. 해외 자료이며 E-19는 기술기업 직원, E-01은 일반 웹 이용자 |
| 무엇을 못 해서 | (가설) 다시 찾을 때 떠오르는 단서(무슨 조사 중이었는지, 대략 언제, 어느 앱에 넣었는지 등)로 그 자료를 찾아내지 못해서. 왜 못 찾는지(원인)는 6절 후보로 열어 둔다 | E-19, E-42 (간접) | 부분. 해외 기술기업 36명 전원이 다시 찾을 세부를 잊은 경험이 있고 매주 이상이 72%였다(E-19). 지식근로자는 다시 찾기에 "어느 정도만" 성공하고 오래된 자료를 찾을 때 덜 성공적이라고 느꼈다(E-42, 영국 51~52명 자기보고). 둘 다 해외이며 국내 대상 확인은 공백 1 |
| 어떤 손해 | (가설) 저장해 둔 자료를 찾지 못해 웹에서 다시 검색하거나 포기하고, 저장한 자료가 작업에 쓰이지 않는다 | E-45, E-44 (증상 예시). 배경: E-18 | 근거 약함. 웹 다시 검색과 포기는 국내 사용자 목소리 각 1건뿐이다: E-45(개발자, 홍보성), E-44(직군·업무 여부 미확인, 직접 쓴 메모). 웹 검색어의 최대 40%가 다시 찾기일 수 있으나 저장한 자료인지는 모른다(E-18). 웹 다시 검색이 실패가 아니라 평소 습관일 수 있다는 대안 해석 있음(5-1 반증 조건 3). 정량 근거는 공백 2·3 |

손해를 지표로 바꾼 후보:

| 대상 | 지표 후보 | 측정 방법 |
|---|---|---|
| 원인 | 다시 찾을 때 떠올린 단서와 실패 원인의 분포. 분류 범주: 조사 주제·목적 / 정확한 제목·검색어 / 출처 사이트 / 대략 시점 / 어느 저장 수단인지 모름 / 시간이 지나 기억 안 남 / 묶음 위치는 알지만 그 안에서 골라내지 못함 / 저장한 사실 자체를 잊음 | 인터뷰에서 최근 실패 사례와 성공 사례를 각각 1건 이상 받아 분류하고, 실패·성공 사이 분포를 비교 |
| 손해: 웹에서 다시 검색 | 저장해 둔 자료를 먼저 저장 수단에서 찾아본 뒤 못 찾아서 웹에서 다시 검색한 횟수(주당). 처음부터 웹 검색한 경우는 따로 센다 | 1~2주 일지(시도마다 "저장 수단을 먼저 찾아봤는가" 기록) |
| 손해: 포기 | 다시 찾기 시도 중 찾지 못하고 그만둔 비율 | 1~2주 일지(시도마다 성공·포기 기록) |
| 손해: 작업에 쓰이지 않음 | 작업에 필요했던 자료 중 저장해 두었는데도 쓰지 못한 비율 | 일지 + 인터뷰 확인 |
| 보조: 시간 비용 | 다시 찾기 한 번에 쓴 시간 | 일지 자기보고 |

## 3. 한 문장 정의

- 현재 문장: 업무 레퍼런스를 저장해 두는 프로덕트 메이커는, / 저장해 둔 자료가 작업에 필요할 때 / 그것을 다시 찾아 쓰려고 하지만, / 떠오르는 단서로 그 자료를 찾아내지 못해(가설), / 웹에서 다시 검색하거나 포기하고 저장한 자료를 작업에 쓰지 못한다(가설).
- 상태: '관찰한 장애'와 손해 모두 가설이다. 인터뷰로 확인되지 않았다(13절 공백 1·2·3). 장애의 원인은 6절에서 다룬다.

## 4. 용어 사전

| 용어 | 정의 | 쓰지 않을 표현 |
|---|---|---|
| 자료 | 사용자가 나중에 쓰려고 저장하는 링크·파일·논문·영상·이미지 등 모든 대상 | 미디어, 콘텐츠, 아이템 |
| 업무 레퍼런스 | 자료 가운데 회사 업무(기획·개발·디자인)에 쓰려고 저장한 것. 개인 사이드 프로젝트용은 넣지 않는다 | 레퍼런스 자료, 참고 자료(혼용 금지) |
| 저장 | 자료를 어딘가에 넣어 두는 한 번의 동작. 분류는 포함하지 않는다 | 아카이빙·아카이브(동작을 말할 때), 스크랩, 클리핑 |
| 저장 수단 | 자료를 넣어 두는 개인용 앱·기능(브라우저 북마크, 메신저 나에게 보내기, 나중에 읽기 앱, 개인 노트 앱, 레퍼런스 전용 앱, 사진첩, 컴퓨터 폴더 등). 팀 공용 공간과 열어 둔 브라우저 탭은 넣지 않는다 | 저장소(아카이브와 혼동) |
| 아카이브 | grep 안에서 저장된 자료가 모이는 곳 | 보관함, 서랍 |
| 분류 | 자료에 폴더나 태그를 정해 붙이는 일 | 정리(분류를 뜻할 때), 카테고라이징 |
| 태그 | 자료에 붙는 분류 꼬리표. 자동·수동 모두 포함 | 라벨, 카테고리, 해시태그 |
| 맥락 정보 | 저장물에 남는 저장 당시의 정보: 출처, 저장 시점, 조사 주제·목적 | 메타데이터(사용자 대상 문서에서) |
| 단서 | 다시 찾을 때 사람이 떠올리는 정보(무슨 조사 중이었는지, 대략 언제, 어느 사이트 등) | 힌트, 키워드(검색어와 혼동) |
| 검색어 | 검색창에 입력하는 단어 | 키워드 |
| 다시 찾기 | 예전에 저장한 자료를 필요할 때 찾아내는 일 | 재검색(웹 검색과 혼동), 리파인딩, 걸러 찾기 |
| 다시 쓰기 | 찾아낸 자료를 실제 작업에 활용하는 일 | 재방문(열람만 뜻하므로) |
| 재방문 | 저장한 자료를 다시 여는 일. 다시 쓰기와 구분한다 | — |
| 조사 세션 | 한 주제를 알아보려고 연속해서 탐색·저장하는 시간 묶음 | 리서치, 래빗홀 |

## 5. 범위 규칙

- 포함: 개인이 업무 레퍼런스를 저장하는 순간부터 다시 찾아 다시 쓰는 순간까지
- 포함 대상: 개발자·PO·디자이너 세 직군. 인터뷰에서 직군별 차이를 본다
- 포함 자료 형식: 링크, 이미지·스크린샷, 문서·논문 PDF, 영상, 로컬 파일 등 모든 형식
- 제외: 팀 협업 문서 관리, 조직 내부 정보 검색, 클라우드 백업 자체, 소셜미디어 여가 저장(인스타 저장 등은 저장 수단으로만 다룸)
- 근거 분포 주의: 확보한 근거는 웹 링크·북마크·이메일·PC 파일에 몰려 있고, 논문 PDF·영상은 거의 없다. 형식별 차이는 인터뷰에서 따로 묻는다(13절 공백 5).
- 일반화 금지 예시:
  - 북마크 연구(E-01)로 논문·영상·파일 전체의 다시 찾기를 말하지 않는다.
  - 이메일·PC 파일 분류 연구(E-09, E-10, E-11)로 링크 저장 행동을 단정하지 않는다. "이메일에서는 ~였다"로 쓴다.
  - 디지털 호딩 연구(E-13, E-14)는 일반 대상 상관연구다. 손해 근거로 쓰지 않는다. 부담감은 인터뷰로 따로 확인한다.
  - 재방문(열람) 수치로 다시 쓰기를 말하지 않는다.
  - "저장한 글의 82%는 읽지 않는다"는 출처가 없다(E-07). 쓰지 않는다.

## 5-1. 반례와 반증 조건

| 반례 페르소나 (가상) | 근거 | 이 사람에게 문제가 약한 이유 |
|---|---|---|
| 검색으로 충분히 찾는 사람: 저장 수단의 검색이나 웹 검색만으로 대부분 다시 찾는다 | E-05(해외 2004년 12명 과제에서 시행의 93%가 첫 방법으로 성공), E-10(이메일에서는 검색이 폴더보다 효과적), E-19(해외 36명 중 52%가 다시 찾기 전략이 자주 통한다고 응답) | 조사 주제를 몰라도 검색어가 떠오르면 찾을 수 있음 |
| 저장을 안심용으로 하는 사람: 다시 쓸 생각보다 "나중에 못 찾을까 봐" 저장한다 | E-04(26/35가 미래 쓸모 때문에 저장, 일부는 거의 안 보지만 못 지움) | 다시 쓰기 실패를 손해로 느끼지 않을 수 있음 |

문제 자체에 대한 반증 조건 (5단계 인터뷰 8~12명 기준, 정확한 n은 5단계에서 확정):

1. 응답자의 2/3 이상이 저장한 자료를 검색으로 문제없이 찾는다고 답한다. 이 경우 문제 질문을 다시 쓴다. (E-19 해외 36명에서는 52%가 다시 찾기 전략이 자주 통한다고 답했다. 국내 대상에서 같은 질문으로 다시 확인한다.)
2. 다시 찾기 실패보다 "저장한 걸 아예 잊는다(다시 찾을 생각을 안 한다)"가 과반에서 주된 문제로 나온다. 이 경우 문제는 다시 보여 주기(재노출) 쪽으로 옮긴다. 주의: 스크리너가 "최근 4주 안에 다시 찾으려 한 적이 있는" 사람만 뽑으므로 이 집단은 구조적으로 걸러진다. 스크리너에서 이 조건 때문에 탈락한 응답자 비율을 따로 기록하고, 그 비율이 높으면 이 조건을 뺀 비교군을 둔다.
3. (손해) 일지에서 웹 다시 검색의 과반이 저장 수단을 먼저 찾아보지 않고 처음부터 일어났다. 이 경우 웹 다시 검색은 실패의 손해가 아니라 평소 습관으로 보고 손해 문장에서 뺀다.

원인 후보별 반증 조건은 6절에 둔다.

## 6. 가설 레지스트리

2단계에서 작성한다. 1단계 범위 확정에서 원인은 열어 두기로 했고(12절), 아래 후보를 2단계에서 같은 기준으로 검증한다. 모두 (가설)이다.

| 후보 | 내용 | 근거 | 반대 근거 | 반증 조건(인터뷰 8~12명 기준) |
|---|---|---|---|---|
| 원인 후보 A: 조사 주제·목적이 남지 않음 | 저장할 때의 조사 주제·목적이 저장물에 남지 않아 그 단서로 찾지 못한다 | E-34(문서 이야기 과제에서 목적이 꽤 자주 등장, 실제 찾기 아님), E-41(참고: 북마크 이용자의 맥락 정보 요구, 정의 미확인) | E-10(이메일에서는 미리 폴더로 분류해도 다시 찾기가 나아지지 않음), E-35(웹 내용 변경 사례에서 경로가 중요해 보임) | 실패 사례의 단서·원인 중 조사 주제·목적이 1/3 미만이고 다른 범주 하나가 과반. 또는 주제별 폴더·컬렉션을 쓰는 사람도 비슷한 빈도로 실패(배경 E-48: 폴더는 프로젝트 이해를 담은 정보) |

## 9. 경쟁 서비스

공개 자료 기준이며 직접 사용 확인은 하지 않았다. 상세 표는 [경쟁 서비스 조사](competitors.md)에 둔다. 4단계에서 포지셔닝을 확정한다.

## 10. 사용자 리서치

5단계 산출물을 일부 앞당겨 [페르소나 초안](personas.md)을 만들었다(대상 7명, 반례 4명, 스크리너 초안). 모두 가상 인물이며 인터뷰 가이드는 5단계에서 만든다.

## 11. 해결·지표

- 해결 방향 한 문장 (팀 아이디어, 검증 전): 쉽고 빠르게 저장하면 태그와 맥락 정보가 자동으로 붙어, 나중에 한 번에 다시 찾을 수 있게 한다.
- 1단계에서 생긴 연결 문제(7단계에서 다룸): 원인은 6절 후보로 열려 있고 해결은 "자동 태그"가 중심이다. 이메일에서는 폴더보다 검색이 다시 찾기에 효과적이었고(E-10), 이메일·PC 파일에서는 태그로 찾을 때 성공률이 낮고 느렸다(E-11). 해결의 중심을 태그로 둘지, 맥락 단서로 다시 찾기로 둘지 정해야 한다.
- 설계 단서(가설): 자동 분류는 사용자가 승인·수정할 수 있을 때 수용성이 높을 수 있다(E-23, E-24 간접).
- 설계 단서(가설): 화면 기록을 타임랩스로 보여 주면 웹 페이지 다시 찾기가 빨라졌다(E-37, 대학생 20명 실험). 라이프로그 사례 연구 1건에서는 맥락 기반 기능이 기대만큼 자주 쓰이지 않았지만 쓰였을 때는 다시 찾기 효과를 높였다(E-39). 인과 맥락 기반 파일 검색은 결과 평가가 평균 17% 높았지만 "쉽게 찾는다"는 자기 평가에는 차이가 없었고 실제 찾기 시간은 측정하지 않았다(E-38). 맥락 정보는 사용자 입력 없이 남고, 다시 찾는 화면에서 자연스럽게 보여야 할 수 있다.
