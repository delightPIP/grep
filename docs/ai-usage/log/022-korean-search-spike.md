# 2026-11-25 · 한국어 부분 검색 스파이크

- 작성자: @carti1108
- 이슈·PR: #4, #5
- 커밋: 없음(커밋 전)

> **요약** 데모 필수 기능인 찾기(F3)가 걸린 한국어 부분 검색을 로컬 Docker에서 실험했다. 인덱스 없는 ILIKE는 사용자 1만 건에서 쿼리당 약 0.9초, pg_trgm은 2글자 검색어에서 인덱스를 쓰지 못했고, PGroonga는 모든 검색어에서 수 ms 안에 같은 결과를 냈다. 검색은 처음부터 PGroonga로 하기로 ADR-BCK-002를 고쳤다.

## 사용 도구

Claude Code(Claude Opus 5.5), Docker(groonga/pgroonga 이미지, Postgres 17), 웹 검색, GitHub CLI.

## 요청

PO가 PR #5에서 가장 먼저 확인해 달라고 한 한국어 부분 검색 스파이크를 진행해 달라고 했다.

## AI 산출물

- 로컬 Docker 실험 환경과 실험 데이터(사용자 5명 × 1만 건), 세 방법(인덱스 없는 ILIKE, pg_trgm, PGroonga) 비교
- ADR-BCK-002 결정 4 수정안, 백엔드 설계 문서 7절 결과 기록, PR #5 답글 초안

## 사람의 판단

- Supabase 프로젝트 대신 로컬 Docker로 먼저 실험하는 것을 받아들임
- 검색을 처음부터 PGroonga로 하는 안을 채택함

## 검증

실험 쿼리를 사용자 한 명 범위에서 검색어 7개 × 5회 실행해 평균 시간과 찾은 건수를 비교했다. `bash Scripts/check-docs.sh`와 `bash Scripts/check-stage-sensors.sh`를 실행했고 통과했다.

## 검증하지 못한 것

1. Supabase 서버에서의 속도(로컬 Windows Docker에서만 쟀다)
2. 한 글자 검색어
3. 실제 사용자 자료(실험 데이터는 단어를 무작위로 이어 만든 글이다)

## AI의 오류와 정정

1. 처음 만든 실험 데이터 생성 쿼리가 모든 행에 같은 글을 넣었다(상관 없는 서브쿼리가 한 번만 실행됨). 고친 뒤에도 어휘가 적어 모든 행에 검색어가 들어갔다. 검색어를 일부 자료에만 넣도록 다시 만든 뒤 측정했다.
2. 앞서 백엔드 설계에서 "사용자 수천 건이면 인덱스 없는 검색으로 충분하다"고 추정했다. 실험해 보니 1만 건에서 쿼리당 약 0.9초로 데모 기준에 빠듯했다. 추정을 실측으로 바로잡았다.
